# Tyflow 性能基线（内网 B 端监控产品专用）

本文件是性能门禁的**依据来源**。`WORKFLOW.md` 和 `RULES.md` 的性能相关条目都以本文件为准。

## 0. 为什么重写默认阈值

听云前端是**内网部署、桌面浏览器、数据密集、图表/表格/拓扑多、页面长时间停留并实时刷新**的 B 端产品。直接套用 Lighthouse 默认的「移动端 + 4G 节流 + Core Web Vitals 公网阈值」是错误的度量。本基线做四条根本性修正：

1. **测量环境**：用 **桌面 preset、无网络节流（或局域网档）**，不用移动端 4G 模拟。
2. **测量对象**：**只在生产构建产物上测**（`npm run build` 后 serve `dist`）。dev server（未压缩、未 tree-shake、带 HMR）的数据**只能作为风险参考，不作为门禁判定依据**。
3. **指标语义**：B 端主内容常依赖大查询，**不把 LCP 当硬门槛**；改为约束「**骨架屏/壳层必须先出，主数据区不允许白屏等待**」+ 工程预算。
4. **不只管首屏，更要管"打开之后"**：监控产品真正的痛点在长时间停留、高频交互、实时刷新、大数据量渲染。**首屏指标（第 2 节）只是一半，运行时性能（第 3 节）+ 内存（第 4 节）同等重要。**

## 1. 门禁按流程等级分流（核心）

性能不是对每个需求都跑全套，而是按 L 级别和「是否触碰首屏/渲染链路/大数据渲染」分流：

| 等级 | 是否跑性能门禁 | 要求 |
| --- | --- | --- |
| **L1**（小 bug/样式/文案） | 否 | 不要求跑 Lighthouse；仅当改动涉及首屏渲染链路时升级到 L2 标准 |
| **L2**（普通页面/接口接入） | 条件性 | **默认只做「工程化检查清单」（第 6 节）**，并在 `VERIFY.md` 记录；只有当改动**新增首屏内容、引入重依赖、改渲染链路、渲染大数据量（表格/图表/拓扑）**时才必须跑生产构建测量（第 2 节）+ 运行时检查（第 3 节） |
| **L3**（公共组件/复杂图表/高风险） | 是 | 必须跑生产构建测量（第 2 节）+ 运行时性能（第 3 节）+ 内存检查（第 4 节）+ 工程化检查清单（第 6 节） |

> 判定原则：**改了首屏/渲染链路/重依赖/大数据渲染 → 必须量；否则做清单 + 记录风险即可。** 这样既守住性能，又不让每个文案改动都背上 Lighthouse 负担（否则门禁必被绕过）。

## 2. 首屏量化指标（仅生产构建 + 桌面无节流时判定）

| 指标 | 含义 | 及格线 | 目标线 | 验证方式 |
| --- | --- | --- | --- | --- |
| FCP | 壳层/骨架首次绘制 | ≤ **1.5s** | ≤ 1.0s | Lighthouse desktop / Performance API |
| TTI | 可交互时间 | ≤ **3.5s** | ≤ 2.5s | Lighthouse desktop |
| INP | 交互响应延迟 | ≤ **200ms** | ≤ 100ms | Lighthouse / 真实交互 |
| CLS | 累积布局偏移 | ≤ **0.1** | ≤ 0.05 | Lighthouse / Performance API |
| TBT | 主线程阻塞 | ≤ **300ms** | ≤ 150ms | Lighthouse desktop |
| 首屏首包 | 首屏 entry chunk（gzip） | ≤ **350KB** | ≤ 200KB | 构建产物分析 / `build` 输出 |

> 注：**LCP 不作为硬门槛**（B 端主内容依赖查询，受后端响应支配）。但若 LCP 明显异常，需在 `VERIFY.md` 分析瓶颈（接口慢 / 包体积大 / 同步渲染重）并记录。

> **增量防劣化优先于绝对达标**：老页面历史包袱大，绝对阈值常不可达、容易被跳过。判定优先看「本次**不比上次劣化**」（首包体积、TBT、TTI 不退化）；新页面/新组件再对照绝对及格线。详见第 5 节。

## 3. 运行时与交互性能（打开之后，监控产品重点）

首屏只决定"打开快不快"，监控产品大量时间花在"打开之后"——这一节是性能投诉的高发区。

**大列表 / 大表格：**
- 单屏渲染行数有上限：**一次性渲染超过约 100 行必须分页或虚拟滚动**（`react-window` / `react-virtualized` / 组件库虚拟化能力），不允许把上千行直接塞进 DOM。
- 列内的复杂单元格（迷你图、进度、tag 组）在大数据量下要测一次滚动是否掉帧。

**图表（ECharts）：**
- 数据更新用**增量 `setOption`（合并）**，不要每次全量重建实例。
- 大数据量（万级点以上）启用 `dataZoom` / 采样 / `large: true`；option 生成函数**不在主线程同步算全量**。
- 图表实例必须在卸载时 `dispose()`（与第 4 节联动）。

**React 重复渲染：**
- 大盘类页面组件多，列表项 / 图表容器 / 重计算需要 `React.memo` / `useMemo` / `useCallback`，避免「切一个筛选整页重渲染」。
- 怀疑卡顿时用 React Profiler 抓一次，定位 re-render 热点并记录在 `VERIFY.md`。

**高频交互响应预算（B 端核心操作）：**

| 操作 | 含义 | 及格线 | 验证方式 |
| --- | --- | --- | --- |
| 切换时间范围 / 筛选 / 搜索 | 点击到「开始出 loading」 | ≤ **100ms**（不卡输入） | 真实交互 / Profiler |
| 列表排序 / 分页切换 | 交互到结果渲染（数据已就绪） | ≤ **200ms** | 真实交互 |
| 图表 hover / tooltip | 指针到 tooltip 出现 | ≤ **100ms** | 真实交互 |

> 注意区分「等后端」和「卡前端」：等接口返回不算前端性能问题，但**交互后连 loading 都迟迟不出 = 前端主线程被阻塞**，要查。

## 4. 内存与泄漏（实时刷新页面的隐形杀手）

监控页常挂着几小时并轮询/推送刷新，泄漏会让内存持续增长直到卡死。**实时刷新 / 长停留页面必查：**

- [ ] `setInterval` / `setTimeout` / 轮询请求在组件卸载时**清理**（`clearInterval` / `AbortController`）。
- [ ] WebSocket / SSE / EventSource 订阅在卸载时**关闭**。
- [ ] 全局事件监听（`window` / `document` / `resize` / `scroll`）在卸载时**移除**。
- [ ] ECharts / 地图 / 拓扑等带实例的组件卸载时 `dispose()`，不残留实例和 DOM。
- [ ] 定时刷新**不无限往数组里追加数据**（如日志流要设上限 / 滚动窗口，否则数组无限增长）。
- [ ] 长跑观察：实时页开着跑一段时间（如反复刷新 5–10 分钟），DevTools Memory 看 JS Heap **不持续单调增长**；可疑时抓两次 heap snapshot 对比 detached node。

## 5. 包体积预算与防劣化

- **首包预算**：首屏 entry chunk（gzip）≤ 350KB（见第 2 节）；新增重依赖前先评估能否懒加载/按需。
- **增量防劣化（推荐做成硬门禁）**：本次构建产物体积 / TBT **不允许比上次劣化**（给一个容差，如 +5%）。把上次值记到 `RETRO.md` / `METRICS.md`，逐次比对，防止"温水煮青蛙"式劣化。
- **包构成分析**：引入重依赖或体积异常时，用 `rollup-plugin-visualizer`（Vite）/ `webpack-bundle-analyzer` / `source-map-explorer` 看构成，定位元凶（常见：echarts 全量引入、moment、lodash 整包、重复打包的依赖多实例）。
- **按需与去重**：路由级 code split；echarts 按需引入 `echarts/core`；antd 等按需；检查同一依赖是否被打进多个 chunk。

## 6. 工程化检查清单（所有涉及 UI 的需求都要过，无需 dev server）

这是比"跑分"更重要、更稳定的部分——直接查代码与渲染链路：

- [ ] 新增路由/大组件是否**懒加载**（`React.lazy` / 动态 `import()`）。
- [ ] 是否把**重依赖**（图表、编辑器、拓扑、xlsx 等）**同步引入首屏**？重依赖必须按需/懒加载。
- [ ] 首屏在「接口慢 / 数据为空」时**是否白屏**？必须有**骨架屏或等价占位**。
- [ ] 骨架屏结构是否**按模块对应真实布局**（不允许只画一个笼统占位块）。
- [ ] 列表/表格是否对**大数据量**有处理（分页/虚拟滚动/限制渲染行数，见第 3 节）。
- [ ] 是否存在**首屏同步执行的重计算**（大循环、深拷贝、同步格式化全量数据）。
- [ ] 实时刷新/长停留页面是否做了**资源清理**（定时器/订阅/监听/图表实例，见第 4 节）。
- [ ] 是否用**接近生产的数据量**验证过（见第 7 节），而不是只用几条假数据。
- [ ] 性能优化是否**改动了业务逻辑**（禁止为性能引入业务行为变化）。

## 7. 测试数据量分档（性能验证必须用接近生产的数据）

监控产品的性能问题只在大数据量下暴露，几条假数据测不出来。涉及列表/表格/图表/拓扑的需求，**性能相关验证必须覆盖以下数据档**：

| 档位 | 用途 |
| --- | --- |
| 空 / 0 条 | empty 态、不报错 |
| 1 条 | 边界、单点图表 |
| 典型量（贴近日常） | 主路径体验 |
| 极端大（贴近生产峰值，如千/万行、万级点） | **性能压力档，必须测**：滚动是否掉帧、交互是否卡、内存是否暴涨 |

> 极端大档可用 mock 批量生成；在 `VERIFY.md` 记录用了多大数据量验证。

## 8. 线上 RUM（dogfooding，长期趋势）

听云自身就是做 APM/RUM 的——**最适合用自家产品监控自家前端**。本地跑分是开发期门禁，线上 RUM 是长期真实数据：

- 产品接入听云前端监控（RUM），采集真实用户的 FCP/LCP/INP、慢交互、JS 错误、慢资源。
- 用**线上真实分布**（P75/P95）校准本文件阈值，而不是只信本地理想环境的单次跑分。
- 关键页面建性能看板 + 劣化告警；上线后看真实指标有没有退化，形成「本地门禁 → 线上验证 → 回灌阈值」的闭环。
- 这是规划性建议，落地节奏按团队接入情况推进；接入后在 `DECISIONS.md` 记录采集口径。

## 9. 测量执行（降摩擦：AI 引导跑并解析，人只看结果）

手动 `build + serve + lighthouse` 摩擦大、容易被跳过。约定：用户说「**跑一下性能 / 验证性能**」时，AI 自动执行下面这套命令、解析 `lh.json`、把指标填进 `VERIFY.md`（**纯执行命令，不维护脚本文件**），人工只确认结果：

```bash
# 1. 生产构建
npm run build
# 2. 本地 serve 构建产物（端口按项目实际）
npx serve -s dist -l 5000
# 3. 桌面 preset、无节流跑 Lighthouse
npx lighthouse http://localhost:5000/<目标路由> \
  --preset=desktop --throttling-method=provided \
  --only-categories=performance --output=json --output-path=./lh.json
```

AI 从 `lh.json` 读出 FCP/TTI/INP/CLS/TBT 与首包体积，对照第 2 节阈值与上次值（第 5 节防劣化），在 `VERIFY.md` 给出「达标/未达标/未量化」结论。

无法跑生产构建/Lighthouse 时：在 `VERIFY.md` 标注「性能未量化」，**并必须完成第 6 节工程化检查清单 + 第 3/4 节运行时与内存检查**（清单是兜底，不能也跳过）。

## 10. 与状态机的衔接

页面请求统一三态 `loading → success / empty / error`（见 `DECISIONS.md` 2026-05-25 页面状态机）：

- `loading` 阶段必须有骨架屏/占位，禁止白屏。
- `empty` / `error` 必须有 `TyEmpty` 等明确态，不允许停在 loading。

## 11. 维护

- 阈值如需调整，先改本文件，再同步 `WORKFLOW.md` / `RULES.md` 的引用句，不要在多处各写一份数值。
- 关键性能数（首包体积、Lighthouse 分、TBT）每次量化后追加到 `RETRO.md`，并聚合进 `METRICS.md` 看趋势（支撑第 5 节防劣化）。
- 调整需在 `DECISIONS.md` 记录背景与依据。
