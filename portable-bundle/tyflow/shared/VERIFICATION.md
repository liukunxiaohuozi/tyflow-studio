# Tyflow 验证与提测规范

开发完成到「提测」之间的唯一一把尺子。所有需求的验证都走这套标准，目的不是"保证零缺陷"（做不到），而是：

> 让「提测」有**客观证据背书**，并把所有 AI 无法自证的部分**显式列给人确认**，绝不默默跳过。

核心原则：**不信任 AI 的"我觉得没问题"，只信任编译器、测试框架和它贴出的原始证据。**

执行来源可以是 Tyflow 原生完整验证，也可以是 Studio 等编排器提供的外部正式测试结果，但准入标准完全相同。未明确进入 `orchestrated` 模式时一律按 `standalone` 执行本文件全部适用检查。复用外部结果必须记录 provider、run ID、代码快照、计划版本/哈希和证据；任一身份不匹配即不可复用。纯 Tyflow 环境不依赖 Studio 或 `frontend-test`，继续执行原生完整验证。

编排模式使用 `TestRequest V1` 冻结需求、步骤、`expectedFiles`、测试用例、代码快照和计划哈希。P0/P1 的通过结果必须带结构化 command/log/screenshot/trace/DOM/coverage/manual 证据；文字结论仅用于说明，不能替代证据。测试前后必须复核代码快照，测试阶段修改业务或配置文件一律阻塞并回到开发审查。

## 1. 三层验证边界

每一项检查都必须明确归到某一层，不允许"中间地带"。

| 层 | 测什么 | AI 能否自证 | 准入边界 |
|---|---|---|---|
| **L1 机器判定** | tsc、eslint、jest、build | ✅ 完全客观 | 机器层二值结果，必须全部通过并贴原始输出；未通过连"部分完成"都不能说。**注意：机器项通过只是必要条件，不等于"可提测"** |
| **L2 行为/契约** | 接口契约一致性、数据映射、三态、关键交互 | ✅ 但要先定清"测什么"（见第 3 节） | 按测试密度矩阵执行 |
| **L3 难自证** | 视觉还原度、业务语义、指标口径、边界体验 | ⚠️ 不能 | 列成人工确认清单，AI 不替你勾 |

## 2. 提测准入门（Definition of Done）

**以下全部满足、且难自证项经人工确认后，AI 才向用户提出是否提交到远程进行测试（不自行闭环提测）**；任何一项缺失只能说「实现完成、验证未通过」，不能说「完成」。

- [ ] L1 机器检查全绿，且**粘贴原始命令输出**（含 jest `Tests: x passed` 行）
- [ ] 增量基线：本次**未新增** tsc / eslint 错误（既有历史债务不计）
- [ ] `TEST_CASES.md` 的 **P0/P1 全部执行且通过**，每条附证据（断言输出 / DOM 快照 / 截图）
- [ ] **规格追踪闭环**：L2/L3 的 P0/P1 Spec ID 均已在 Traceability Matrix 中闭环（实现位置 / 测试用例 / 验证证据 / 状态），无 open/blocked 核心规格
- [ ] **SDD/Traceability 缺口扫描已完成**：无“有规格没测试”“有测试没规格”“有代码没 Spec ID”“specVersion 不一致”“需求外功能未回写规格”等断链问题
- [ ] **测试覆盖率已报告**：给出整体 + 本次改动范围/核心目录的覆盖率（Statements/Branches/Functions/Lines），标注未覆盖的关键分支，供人工确认（覆盖率是参考证据，不是放行 KPI）
- [ ] **需求覆盖度**：`REQUIREMENT.md` 每条验收标准都能追溯到用例 ID + 实现位置，无「未覆盖」
- [ ] **三态都被真实触发过**：loading / success / empty / error（不是只看 success）
- [ ] **字段映射零「待确认」**：`INTEGRATION.md` 无悬而未决的字段语义
- [ ] **难自证项已列清单**并经人工确认（见第 5 节）
- [ ] **国际化产物已确认**：`npm run scan` 已**实际执行并粘贴命令输出**；新增中文均已 `I18nT` 包裹并写入 `zh-CN.json`，`en-US.json` 无残留中文 value（未及翻译的已列为待办）。**grep 扫硬编码中文只用于找遗漏，不能替代 `npm run scan`**（完整通过判定见 §2c）
- [ ] 性能按 `PERFORMANCE.md` 分级处理完毕
- [ ] **可观测性**：新增组件有错误边界、异步有错误/加载处理、图表表格三态完整、关键交互可被 APM 采集（见第 6c 节）
- [ ] **跨浏览器**：关键页面 / 样式 / 交互在 **Chrome + Firefox 最新稳定版**都实测过，无样式错乱或交互失效（附两端截图或说明）
- [ ] **符合观云知识库规范**：目录结构 / 请求与服务层 / 编码与 TS / 样式 token / 组件选型 / 分支与发版符合 `baseline/观云 知识库` 相关专题，任何偏离已在 `VERIFY.md` 写明理由
- [ ] **单一映射点**（涉及接口时）：后端 → UI 契约的映射全部在 service 的 `mapToXxx`，页面/组件内无字段重命名/兜底/转换，后端原始类型（`XxxResp`）未流到页面
- [ ] **字段映射表完整**：`INTEGRATION.md` 逐字段有「来源 / 含义 / 转换 / 证据 / 确认」，无「待确认」；service 映射逐字段注释来源
- [ ] **mock 与契约同构**：mock 符合 UI 契约类型且覆盖三态/边界；关键字段有 shape 漂移检测

## 2b. 测试结果报告（提测时按此结构产出，写进 VERIFY.md）

光说"测过了、通过了"零价值。提测时必须给出**可审计、可挑战**的结构化报告，四部分缺一不可：

1. **用例场景清单**：测了哪些场景，至少覆盖 正常 / 异常 / 边界（空、null/undefined、超长、特殊字符、枚举未知值）/ 顺序与并发相关（如有）。每条标 P0/P1/P2。
2. **输入 → 期望输出 → 实际输出**（关键项逐条）：关键用例列出输入、期望、实际，并**附可复现命令或原始证据**（jest 输出行 / DOM 快照 / 截图 / API 对比），让人能一键重跑证伪。
3. **覆盖标准声明**：明说覆盖到什么程度，例如「覆盖组件 props 常见组合的前 80%」「service 字段映射全分支覆盖」。**禁止用「已全面测试」这种无法证伪的话**。
4. **跳过项说明（最重要）**：哪些场景没测、为什么没测（成本 / 环境限制 / 不确定性 / 难自证）。难自证的进第 5 节人工确认清单，环境受限的写清缺什么。**没有「跳过项」一栏的报告视为不可信**——等于声称全测了。

> 为什么这能让人敢信：报告的每条关键项都带**可复现命令**，你不用通读代码，随手抽一条重跑就能证伪；跳过项一栏强制 AI 暴露边界，把"假装全测了"挡在门外。

**留档与去向**：全量报告写进需求目录的 `VERIFY.md`（含所有原始证据，长期留档）。**经 PR 提交时，把报告摘要写进 PR 描述**——含：用例场景计数（正常/异常/边界/并发 各几条、P0/P1 通过情况）、覆盖标准声明、跳过项、关键证据的可复现命令、难自证项确认状态；写入前做敏感信息脱敏。**业务仓库不另存过程文档**（留档方式见 `DECISIONS.md`）。

## 2c. 国际化通过判定（Definition of i18n Done）

"国际化通过"是一个有明确边界的结论，**必须同时满足以下三条，缺一不可**：

1. **全部包裹**：本次新增/改动的所有中文 UI 文案都已用 `I18nT(...)` 包裹；`grep` 扫硬编码中文无遗漏。
2. **已扫描**：已实际执行 `npm run scan`（贴命令输出），`I18nT` 内容正确写入 `src/locales/zh-CN.json` 和 `src/locales/en-US.json`。
3. **已翻译**：`en-US.json` 中本次相关 key 的 value 已是英文，无残留中文。

只要在测试/验证中发现「有中文未被 `I18nT` 包裹」或「`en-US.json` 仍存在中文 value」，**即判定国际化未通过**，不得宣布完成。处置闭环（按序走完再复核）：

```text
发现遗漏 / 残留 → ① 给未包裹的中文补上 I18nT(...) → ② 重新 npm run scan
→ ③ 翻译 en-US.json 中残留的中文 value → ④ 复核三条件全满足 → 才算「国际化通过」
```

> 关键区分：`grep` 只解决第 1 条「找遗漏」；`npm run scan` + 翻译解决第 2、3 条「产物正确」。三条都过才是通过，不能用任一单步代替整体结论。

## 2d. SDD/Traceability 方案自验证

工作流规则本身不能默认可信。每次引入或调整 SDD/Traceability 规则后，至少用 1 个 L2 需求试点验证规则是否真的提高准确性，试点结果写入该需求 `RETRO.md`，可复用结论再沉淀到 `shared`。

验证方法：

1. **正向试点**：选择一个真实 L2 需求，完整产出 `SPEC.md`、`PLAN.md`、`TEST_CASES.md`、`VERIFY.md`，检查是否能从每条 P0/P1 Spec ID 追到实现、测试和证据。
2. **反向缺陷注入**：人工或 AI 有意制造 3 类断链样例并确认流程能发现：
   - `SPEC.md` 有 P0/P1 Spec ID，但 `TEST_CASES.md` 没有对应用例。
   - `TEST_CASES.md` 有用例，但没有对应 Spec ID。
   - 代码中出现需求外改动，但 Traceability 找不到对应 Spec ID。
3. **抽样复核**：人工随机抽 3 条 Spec ID，对照代码和验证证据，确认描述、实现、测试和实际行为一致。
4. **成本评估**：记录新增耗时、人工确认次数、发现的断链数、修正后是否减少返工。
5. **规则调整**：如果检查项频繁误报、难执行或不能发现真实问题，记录到 `shared/FEEDBACK.md`，复盘后调整模板或门禁。

判断标准：

- 至少发现或预防 1 类真实断链，或能明确证明当前需求所有 P0/P1 规格闭环。
- 人工抽样未发现 Spec 描述、实现和验证证据不一致。
- 新增流程成本可接受；若成本明显高于收益，仅保留在 L2 高风险 / L3 场景。

## 3. 测试密度矩阵（定"测什么"）

不是所有代码同等强度。按类型定密度，把测试投到最容易出 bug 的地方：

| 代码类型 | 要求 |
|---|---|
| 数据转换 / `service` 字段映射 / 图表 option 生成 | **必须单测**，覆盖：正常 + 空数组 + null/undefined + 枚举未知值 + 超长/特殊字符 |
| 自定义 hook | 必须 `@testing-library/react` 测 |
| 筛选 / 排序 / 分页 / 搜索等带参交互 | 必须 Playwright 或集成测试触发一次，断言状态变化 |
| 纯展示 UI 组件 | 不强制（抽离出的纯逻辑才测） |
| 配置 / 常量 | 不测 |

## 4. 防 AI 刷假测试（验证可信度的根基）

AI 自主写测试的最大风险是**自我实现的假测试**（断言它自己刚写的逻辑，100% 通过但毫无意义）。以下 5 条反模式 review 时强制扫描（与 `RULES.md` 自动化测试节一致）：

1. **测行为不测实现**：断言用户可见输出，不断言内部 state / 私有方法。
2. **不镜像实现**：测试用字面量做预期（`toBe(3)`），禁止在测试里复算预期。
3. **边界 mock 不中间 mock**：只在网络/时间/随机/第三方 SDK 边界 mock，业务链路保持真实。
4. **杜绝 flaky**：禁止真实 `setTimeout`，用 fake timers；不依赖随机和真实时间戳。
5. **真实断言**：每个 test 至少一个有意义的 `expect`；禁止 `expect(true).toBe(true)` 和空测试。

> 没有这 5 条，前面所有"测试通过"都可能是假的。

## 5. 难自证项处理（L3）

AI 无法客观证明的部分——视觉还原度、业务语义、指标口径——处理方式：

- AI 把这些项**集中列在 `VERIFY.md` 顶部的「待人工确认」清单**，写清楚"AI 的判断 + 不确定点"。
- **默认（可调）：提测前必须人工扫一眼确认这份清单**，确认后才算过提测准入门。
- AI 绝不替人勾选难自证项，也不得因为"看起来对"就归入已通过。

有 Figma / 设计稿 / **Open Design 原型**时，AI 先按这份「设计还原度自检清单」逐条核对并把结论写进 `VERIFY.md`，再交人工确认（无设计稿则注明「无设计稿，跳过」）：

### Open Design 基准（有 `OD_HANDOFF.md` 时）

- 读取 `handoffPath` 与 `handoffVersion`，写入 `VERIFY.md` 头部。
- 逐条执行 `OD_HANDOFF` 的 `acceptance`（按 `odRef` 定位 OD 屏与 DOM 区域）。
- `tokenMap` 中 **must-match** 项：对照实现页 computed style 或项目 design token。
- 打开 OD `screens/<对应屏>.html` 与实现页并排：布局分区、关键交互、三态。
- `TEST_CASES.md` 设计还原度用例必须引用 acceptance id（如 A1–A18），基准写 OD 路径而非 PNG。

- 整体布局：左右结构 / 上下分区 / 宽高比例与设计稿一致。
- 间距、字号、颜色对齐设计 Token（允许 1–2px 偏差，不允许明显差异）。
- 表格列宽、表单项排列、按钮位置一致。
- 图表类型、配色、图例位置一致（数据可 mock，但结构必须对）。
- 交互状态覆盖设计稿所有变体：默认 / hover / active / disabled / 选中 / 展开收起。
- 弹窗 / 抽屉 / 下拉的尺寸和位置一致。
- 有响应式设计时，断点下表现合理。

> 这是把"自动化"和"质量兜底"分开的关键阀门。若团队后续接受更高自主度，可改为"AI 自动提测 + 清单事后审查"，在 `DECISIONS.md` 记录该调整。

## 6. B 端监控产品专属验证（本场景必加）

通用规范盖不住监控产品的坑，这几条单独定：

- **图表测「数据→option 映射」**，而非只看"渲染出了一张图"。option 生成函数单测：空数据、单点、负值、超大值。
- **异常数据态**：无数据时段、null 指标、超长维度名、特殊字符，必须有用例。
- **时间范围 / 查询参数**：用**真实参数**调一次（分页、筛选、时间窗），不能用默认值凑合。
- **大数据量渲染**：列表/表格在大数据量下是否分页/虚拟滚动，不能只测 10 条。

## 6b. 跨浏览器兼容（Chrome + Firefox 都必须过）

只在 Chrome 跑通不算完成——很多样式/布局问题切到 Firefox 才暴露。

- **提测前关键页面/交互在 Chrome 和 Firefox 最新稳定版各实测一遍**，对照设计稿无样式错乱、无布局塌陷、无交互失效；附两端截图或说明。
- 主动规避高发差异点：
  - 私有前缀：慎用只带 `-webkit-` 的属性，需补标准属性或 Firefox 方案。
  - 滚动条：Firefox 用 `scrollbar-width` / `scrollbar-color`，`::-webkit-scrollbar` 在 Firefox 无效。
  - 表单/日期/`select` 等原生控件默认样式两端不同，按需统一。
  - flex/grid 细节、`gap`、`backdrop-filter`、`appearance`、字体渲染差异。
- 命中并解决的差异 → 在项目 `projects/<project>/LESSONS.md` 记一笔，避免后续复犯。

## 6c. 可观测性检查（监控产品必做，开发期就要具备）

听云本身做 APM/RUM，新代码必须「可被观测」，这不是收尾补丁：

- 新增组件有**错误边界**（ErrorBoundary 或等价），异常不整页白屏崩溃。
- 异步操作有**错误处理 + 加载状态追踪**（呼应 loading/empty/error 三态）。
- 图表 / 表格的**空态、加载态、错误态**完整。
- 关键交互有**性能标记、可被 APM 采集**（页面加载、接口调用、渲染耗时）。
- 新增页面已接入项目**监控埋点**（如有）。

## 7. 无测试基建时怎么办

项目若没配好 jest / Playwright（如某项目 E2E 未配置）：

- **默认：如实在 `VERIFY.md` 标注「未配置，跳过」，照常走人工探索性测试 + 现有手段验证**，绝不伪造通过。
- **例外：核心纯逻辑（数据转换 / mapper / 图表 option）即使在无 E2E 项目也应补最小 jest 单测**——这类 bug 代价最高且最易测。
- 各项目当前能力以 `shared/PROJECTS.md` 的「E2E 状态 / 测试命令」字段为准。

## 8. 证据与失败处理

- 每条声明附**原始证据**（命令输出 / DOM 快照 / 测试输出行 / 截图），不允许只写「已通过」。
- 修复后**只重跑失败项**，但**保留原始失败记录**，不抹掉历史。
- 验证失败 → 只能写「实现完成，验证未通过」，列出失败项与修复方向；不得写「完成」。
- 所有结果落到需求目录的 `VERIFY.md`，对齐本文件的准入门逐项打勾。
