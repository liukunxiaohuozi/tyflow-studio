# Tyflow 规则

## 核心规则

- 以 `shared/WORKFLOW.md` 中的工作流作为事实来源；`shared/` 整体（WORKFLOW/RULES/VERIFICATION/PERFORMANCE/SECURITY/DECISIONS/TRUST/METRICS/registry/projects）是唯一事实来源。
- `workfile/` 与 `skills/document/` 下的文档是**历史版本 / 说明性归档**，仅供版本复盘与学习，**不是事实来源**：执行 tyflow 时不得据其行动，检索到也不得引用，凡与 `shared/` 冲突一律以 `shared/` 为准（这些旧文档可能残留单一 `CURRENT.md`、组件索引缓存、旧脱敏写法等**已废弃**约定，照做会出错）。
- **开发必须遵循 `baseline/观云 知识库`**：开发前先读 `baseline/观云 知识库/knowledge-base-entry.md`，按其「任务路由」只读 1–2 份相关专题（`engineering/` 工程、`design/` 设计、`components/` 组件），不整库加载。实现、样式、请求与服务层、目录结构、分支与发版都以知识库规范为准。冲突时按优先级裁决：**目标仓库真实代码 > 用户当前指令 / 项目输入（PRD/Figma/联调约束）> 知识库 > 历史归档**。任何偏离知识库的做法必须在 `VERIFY.md` 写明理由。
- 默认入口是 `tyflow-do`；自然语言别名是 `Tyflow` 或 `听云前端工作流`。
- 实现前先将工作分为 L1、L2 或 L3。
- 每个任务都要保留验证和复盘；L1 可以缩小范围，但不能跳过。
- 如果需求没有理解清楚，先停止并向用户澄清，再开始实现。
- L2/L3 中 `SPEC.md` 是开发真源。PRD、截图、Figma、Open Design、接口材料和口头补充都是输入源；实现、计划、测试和验证必须追溯到 `SPEC.md`。没有 Spec ID 的需求外实现不得落代码。
- L2/L3 的 `SPEC.md` 必须包含稳定 Spec ID、`specVersion`、状态、Change Log 和 Traceability 初始表。P0/P1 规格必须能追溯到实现位置、测试用例和验证证据。
- 需求目标、范围、交互、字段语义、验收标准、接口契约或状态模型发生变化时，必须先更新 `SPEC.md`，再同步 `PLAN.md`、`TEST_CASES.md`、`CONTRACT.md` / `INTEGRATION.md`（如涉及接口）和验证项；影响范围或验收标准的变化必须重新人工确认后才能继续开发。
- L2/L3 进入开发前必须先写 `PLAN.md`，并经过人工审查确认；未确认计划不得开始改代码。先规划再开发是强制门禁，不是建议。
- `PLAN.md` 必须包含「模块复用决策」：逐模块写明属于 `复用现成组件` / `使用项目二次封装` / `本地改造` / `新封装` 中的哪一种，并写依据；判定为「新封装」的必须说明为什么不能复用。没有这张决策表的计划视为未完成，不得进入开发。
- L2/L3 进入开发前必须根据需求文档和 `SPEC.md` 生成 `TEST_CASES.md`；每条 P0/P1 用例必须引用对应 Spec ID，开发完成后必须按测试用例逐条验收。
- 新生成的 L2/L3 计划必须使用严格追踪：每个计划步骤显式填写覆盖的 Spec/需求 ID 和 `expectedFiles` 文件或 glob 范围，每个 P0/P1 用例显式填写 `covers`、`verifies` 和优先级。旧计划的全量兼容映射只能用于查看，不得通过开发门禁。
- 人工审查 `PLAN.md` 和 `TEST_CASES.md` 时必须确认任务拆分、改动范围、风险点、验证方式、是否需要 TDD/review、验收用例是否覆盖需求，以及是否存在待确认业务语义。
- 输出 `PLAN.md` 和 `TEST_CASES.md` 后必须停下来询问“是否可以按此开发计划和测试用例开始开发？”，收到人工明确确认前只能修改计划、测试用例、补充信息或回答问题。
- 如果人工在审查中修改计划，或要求 AI 辅助调整计划，调整完成后必须再次询问是否可以按更新后的计划开发；未再次确认前仍不得进入开发。
- “可以”“按这个计划开发”“确认”“开始开发”等明确授权才算通过；沉默、泛泛讨论、只确认局部内容不算通过。
- `VERIFY.md` 必须引用 `TEST_CASES.md` 的执行结果，并维护 Traceability Matrix（Spec ID → 实现位置 → 测试用例 → 验证证据 → 状态）；未执行 P0/P1 验收用例、P0/P1 Spec ID 未闭环或存在 open/blocked 核心规格时，不得宣布完成。
- 验证阶段必须执行 SDD/Traceability 缺口扫描：检查“有规格没测试”“有测试没规格”“有代码改动没 Spec ID”“specVersion 不一致”“需求外功能未回写规格”。命中任一核心断链时，只能判定「实现已完成，验证未通过」或回到 SPEC/PLAN/TEST_CASES 修订。
- 验证执行模式默认是 `standalone`，必须执行 Tyflow 原生完整验证。只有调用方明确提供 `orchestrated` 编排标识并承诺后续正式测试时，开发阶段才可跳过完整完成前验证；此时不得生成最终验证结论或声称可提测。外部结果必须匹配当前代码快照、计划版本/哈希、必测用例和证据，否则回退原生完整验证；部分覆盖只能补测缺口，不能冒充完整通过。
- P0/P1 自动化用例判定通过时必须提供结构化证据；只有文字描述不算通过证据。编排测试期间只允许新增或修改测试文件和受控证据，业务代码、依赖、路由、权限或配置发生变化必须返回开发阶段并重新执行差异审查。
- 提测时必须产出结构化「测试结果报告」（见 `VERIFICATION.md` 第 2b 节），四部分缺一不可：① 用例场景清单（正常/异常/边界/并发）② 关键项 输入→期望→实际 + 可复现命令或原始证据 ③ 覆盖标准声明（禁止「已全面测试」这类无法证伪的话）④ 跳过项说明（没测什么、为什么）。**缺「跳过项」一栏的报告视为不可信**。每条关键证据必须可被人工一键重跑证伪。全量报告留需求目录 `VERIFY.md`；经 PR 提交时把报告摘要（场景计数 / 覆盖率 / 跳过项 / 关键证据可复现命令 / 难自证项确认状态）写进 PR 描述并脱敏，业务仓库不另存过程文档。
- 不要猜测需求细节，也不要通过改变业务逻辑来做优化。
- **联调单一映射点**：后端 → UI 契约的映射只允许写在 service 的 `mapToXxx`；页面/组件禁止字段重命名、兜底、类型转换、枚举翻译；后端原始响应类型（`XxxResp`）不得流到页面。排查任意字段问题的路径必须唯一——指向该模块 service 的 `mapToXxx`。
- **契约分层**：UI 契约（`XxxVO`/`XxxModel`，稳定）与后端响应（`XxxResp`/`XxxDTO`，易变）分开定义、命名区分；页面只依赖 UI 契约。后端未给接口定义不阻塞——按页面需求自定 UI 契约 + 自造 mock 先开发，接口到位后只补 service 映射这一步。
- **字段变更分级**：非契约级变更（改名/挪层级/换枚举/加包装壳）只改 `mapToXxx` 一处，页面/组件/契约不动；契约级变更（展示内容真的增减）才动契约和页面并回到计划确认。
- **联调输入与抓包**：优先用接口文档+样例或浏览器抓包（`ide-browser` MCP，token 留在浏览器）获取真实数据；原始 cURL/token/cookie 不进对话上下文、不落盘；调不通时说明阻塞点、**绝不静态硬猜接线**，改用样例/抓包或回退 mock。
- **映射可定位**：service 映射逐字段注释来源，`INTEGRATION.md` 维护字段映射表（UI 字段 ← 后端来源 / 含义 / 转换 / 证据 / 确认）；关键字段加 shape 漂移检测。详见 `baseline/观云 知识库/engineering/request-and-service.md`「契约层可定位性规范」。
- 合并代码或宣布完成前必须审查代码；不要跳过 review。
- 遇到死路 / 重试 ≥ 2 次仍失败 / 要换方案或推翻计划 / 卡住找人工前，必须在需求目录 `ATTEMPTS.md` 记一笔（目标、尝试、卡点、处置、状态）；换方案前先回看 `ATTEMPTS.md` 是否已记过此路不通，避免反复撞同一堵墙。属于「工作流 / 门禁 / 规则本身行不通」的，记到 `shared/FEEDBACK.md`。复盘时把可复发的死路升到项目 `LESSONS.md` 或规则。可调用 MCP 工具 `tyflow-feedback`（`log_attempt` / `log_feedback`）直接追加，无该工具时直接编辑文件。
- 检查新引入组件是否懒加载或按需加载。
- 将性能视为开发阶段门禁，而不是收尾清理项。
- 检查前端渲染慢或 API 响应慢时是否有白屏风险。
- 对存在加载风险的页面，使用与模块布局匹配的骨架屏。
- 不要创建只大致近似布局的骨架屏；骨架屏必须反映真实模块结构。
- **跨浏览器兼容是硬要求**：所有新开发或修改的页面、样式、交互必须在 **Chrome 和 Firefox 最新稳定版**都正常，不允许「Chrome 正常、切到 Firefox 样式错乱」。提测前必须在两个浏览器都实测过关键页面与交互。常见差异要主动规避：慎用只带 `-webkit-` 前缀的属性（需补标准属性或 Firefox 对应方案）、滚动条样式（Firefox 用 `scrollbar-width` / `scrollbar-color`，不是 `::-webkit-scrollbar`）、表单/日期控件默认样式、flex/grid 细节、`backdrop-filter` 等。命中并解决的差异在对应项目 `projects/<project>/LESSONS.md` 记一笔，避免复犯。
- 不要保存原始 cURL、cookie、token、私密认证头或未脱敏响应。
- 脱敏是 AI 的强制自查动作：向 `shared` 沉淀或分享 `.tyflow` 前，AI 必须逐条通读待写入内容，命中 token/cookie/Authorization/Bearer/JWT/私钥/自定义认证头/URL 凭证/原始 cURL/未脱敏响应等即先脱敏再写入；目标代码项目侧由 gitleaks pre-commit + CI 兜底。完整策略见 `shared/SECURITY.md`。
- 不要靠猜测绑定 UI 字段。必须记录字段来源、转换规则、状态和证据。
- 对听云详情类 API，当下游查询参数需要结束时间时，优先使用详情 API 返回的 summary end time，而不是 URL endTime。如果返回的 endTime 为 0，将其视为“现在”，并使用当前时间戳格式化查询时间和计算时间窗口。
- 开发过程中所有新写中文 UI 文案都要先用 `I18nT(...)` 包裹；不要每新增一处文案就运行 `npm run scan`。等静态页面结构和主要文案集中完成后，再统一运行一次 `npm run scan`，并在交付前翻译 `en-US.json` 中仍为中文的 value。`grep` 扫硬编码中文只用于找遗漏，**不能代替 `npm run scan`**（找遗漏 ≠ 确认产物）；scan 未实际执行并粘贴输出，不得宣布国际化检查通过。「国际化通过」的完整判定：全部中文已 `I18nT` 包裹 + `npm run scan` 已跑 + `en-US.json` 无残留中文，三条缺一不算通过；测试中发现遗漏或残留，按「补包裹 → 重跑 scan → 翻译 → 复核」闭环处理（见 `VERIFICATION.md` §2c）。
- 标准图表使用 ECharts 或项目已有 ECharts 封装实现。
- 不要把 Figma 图表复刻成静态 SVG/canvas/固定 JSX。
- 识别到目标项目后、以及每次执行前，必须先读 `shared/projects/<project>/LESSONS.md`（项目错题本），把与本次需求相关的条目当作硬约束，避免重犯历史上已被纠正过、易复犯的错误；不存在则按 `shared/projects/README.md` 新建。
- 编写新 UI 前，先搜索项目已有组件和模式。
- 跨项目组件默认只是参考资产，只有完成风险评估后才复制。
- L2/L3 复盘必须判断本次经验是否能沉淀为下一次默认能力；不能只写本次总结。
- 只有已经验证通过、可复用、无敏感信息、不会改变未确认业务语义的经验，才能写入 `shared`。
- 未验证、仅适用于单次需求、依赖本机环境或含有业务不确定性的经验，只能留在需求目录或 `local`，不能升级为共享规则。
- 复盘沉淀必须分为：自动纳入、建议确认、仅本需求记录。影响团队行为、公共组件、接口语义、权限、导航、数据范围的沉淀项必须先人工确认。
- 同一类问题重复出现 2 次以上，必须在复盘中提出规则化建议并落点：全局通用 → `RULES.md` / `DECISIONS.md` / registry；**项目特定 → `shared/projects/<project>/LESSONS.md`（项目错题本）**；并据情况补测试用例、lint 或调整 `TRUST.md` 信任等级。不要让项目特定经验污染全局规则，也不要让它随需求归档丢失。
- 写入共享规则后，必须记录来源需求、适用范围和验证方式；不能只写一句抽象原则。
- 如果沉淀内容和既有规则冲突，暂停并列出冲突，不要直接覆盖旧规则。

## 开发边界（红线，任何等级都不得越过）

- **理解不清必须停下问人工，确认后再动手**。出现以下任一情形，立即停止当前操作、说明卡点、向人工提问，拿到明确答复后才继续，**不得自行假设推进**：
  - 需求文档 / 业务语义没看明白（要实现什么、边界是什么、异常怎么处理）。
  - 组件复用没判断清楚（是否已有现成组件、该复用还是该封装、封装到什么粒度）。
  - 接口联调中字段没理解清楚（字段含义、映射关系、类型、枚举取值、空值/异常语义）。
- **以下行为是红线，禁止触碰**：
  - 不要猜需求、不要猜字段含义。
  - 不要瞎写字段兼容 / 容错（用 `||`、可选链、默认值去"兜"一个自己都没搞懂的字段，是在掩盖问题）。
  - 不要为了开发而开发、不要为了"显得完整"加需求外的东西。
  - 不要重复造轮子（动手前先按 `PLAN.md` 的模块复用决策搜现成的）。
  - 不要"自行以为可以这样"就把 UI 绑定到不确定的接口字段——**错误的字段绑定会埋下难排查的 bug，或导致后续修改方向错误**。
- **必须做到**：先思考、先理解业务、对本次需求负责；每个被绑定的字段都要有来源、转换规则和证据（见上文字段记录规则）。宁可多问一句，不要带着模糊往下写。

## 自动化测试

适用范围：所有 Tyflow 项目；当前主要在 `rum-web` 落地验证，其他项目按各自 `PROJECTS.md` 中登记的能力执行，能力不存在时如实跳过，不得伪装通过。

### 何时必须写 jest 单元/组件测试

- 新增或修改纯函数（`src/utils/` 下、无外部依赖、无副作用）必须配套 jest 单元测试，覆盖正常路径 + 至少 1 个边界用例。
- 新增或修改自定义 hook 必须配套 `@testing-library/react` 测试。
- 修复 bug 时优先补一条复现该 bug 的失败测试，再修代码（回归保护，防止同一 bug 再现）。
- UI 组件（pages/、components/）的测试不强制，但若组件包含可测的纯逻辑（状态机、数据处理），鼓励抽离后单测。
- L1（小 bug、样式微调）可缩小测试范围但不能跳过验证；改了 utils 的 L1 仍需补测试。

### 测试编写规则（5 大反模式，review 时强制扫描）

1. **测行为不测实现**：断言用户可见输出（DOM 文本、返回值、副作用），不断言内部 state、函数被调用次数、私有方法。重构不改行为时测试不应失败。
2. **不镜像实现**：测试里使用具体字面量作为预期值（`expect(add(1,2)).toBe(3)`），禁止在测试里复算预期（`const expected = 1 + 2`）—— 复算等于把生产逻辑抄到测试里。
3. **边界 mock 不中间 mock**：只在外部边界 mock（网络、时间、随机、文件系统、第三方 SDK），业务逻辑链路保持真实。`jest.mock` 同一文件超过 3 个时需要解释必要性。
4. **杜绝 Flaky**：禁止真实 `setTimeout/sleep`，必须用 `jest.useFakeTimers` + `advanceTimersByTime`；网络请求用 mock；不依赖随机数和真实时间戳。
5. **真实断言**：每个 `test` 至少 1 个有意义的 `expect`，禁止 `expect(true).toBe(true)` 和无 `expect` 的空测试（这两种会刷出虚假覆盖率）。

### 验证阶段的强制要求

- `VERIFY.md` 中关于自动化测试的小节必须粘贴**真实命令输出**（包含 PASS/FAIL 计数、Tests 行），不能只写"已通过"或"看起来没问题"。
- 测试失败时不得宣布完成；只能写"实现已完成，验证未通过"，并在 `VERIFY.md` 列出失败用例和修复方向。
- 跑测试必须使用 `PROJECTS.md` 登记的命令；命令不在登记表里时先补登记，不要私自换命令。

### 覆盖率使用原则

- 覆盖率是体检报告，不是 KPI；不为达标而写无断言的"刷数测试"。
- **测试完成后必须报告本次覆盖率占比供人工确认**：至少给出整体覆盖率（Statements/Branches/Functions/Lines）和本次改动范围/核心目录的覆盖率，并指出未覆盖的关键分支。覆盖率是给人工拍板的参考证据，不替人工决定是否可提交远程测试。
- 关注 **Branches** 多于 Lines —— bug 多藏在 if/else 边界。
- 阈值采用棘轮策略（只升不降）：当前值 + 5% 起步，逐步抬升；核心目录（utils/、关键算法）严，UI 组件宽。
- 100% 覆盖率不是目标；80% 之后边际收益急剧下降。

### E2E 测试

- 当前各项目 E2E 状态以 `PROJECTS.md` 中"E2E 状态"字段为准。
- 状态为"未配置"的项目，Tyflow 不得跑 E2E 命令，不得伪造 E2E 通过结果；`VERIFY.md` 如实记录"E2E 未配置，跳过"。
- 若团队后续启用 E2E（推荐 Playwright），需先：选型决策入 `DECISIONS.md` → 装包并跑通 demo → 写 5-10 个核心路径用例 → 配 `npm run test:e2e` → 更新 `PROJECTS.md` 后再启用本节硬规则。
- 在 E2E 启用前，端到端验证依赖人工探索性测试 + jest 集成测试覆盖关键交互。

## Shared 与 Local

- 将可复用、已确认的规则和索引写入 `shared`。
- 将当前状态、缓存、临时笔记和敏感材料写入 `local`。
- 不要把敏感值写入 `shared`。
- `shared` 中的长期规则优先级高于单次 `RETRO.md`；单次复盘只有在被确认并写入 `shared` 后，才成为后续默认约束。
- `RETRO.md` 中的“沉淀建议”默认不是事实来源，后续任务引用前必须检查是否已进入 `RULES.md`、`DECISIONS.md` 或 registry。
- 更新 `shared` 时不要保存原始需求材料、原始 cURL、未脱敏响应、客户敏感数据或只对本机有效的路径。
- 对听云前端 UI，可点击超链接、`a` 标签和 tab 标签必须使用 `#1677ff` 作为可点击文本颜色，除非已有组件 token 明确映射到同一个听云蓝。
- 对听云前端列表/表格 UI，先在目标项目中搜索已有列表/表格组件；如果存在项目本地列表组件，优先使用它。如果项目没有可复用列表组件，则在项目 `components` 目录下按照既有 TableApi 包装模式创建 `CustomApiTable`，再用于后端驱动列表。具体组件选型见 `baseline/component-selection.md`。
- 所有新增或修改的 API 请求参数和响应结构，必须先定义 TypeScript 类型再写业务逻辑；类型定义放在 `types.ts` 或 service 文件头部，不要散落在页面组件中。

## 验证信任

- **提测准入门、三层验证边界、测试密度矩阵、B 端专属用例统一见 `shared/VERIFICATION.md`**；每次提测都走这一把尺子，`VERIFY.md` 按其准入门逐项打勾。
- 验证结果必须是证据驱动的：每条声明附带原始命令输出、DOM 快照、测试输出或截图，不允许只写「已通过」或「看起来没问题」。
- 硬检查（tsc、eslint、jest、build）不可跳过，输出是机器生成的二值结果，AI 无法伪造。
- 验证按固定顺序执行：硬检查 → 测试用例 → 需求覆盖度 → Playwright 页面验证。任何一步失败不得继续往下。
- VERIFY.md 结论中的五项复选框（硬检查通过、P0/P1 用例通过、需求无核心遗漏、性能达标、风险已记录）必须全部勾选才能判定「可以提测」。
- 验证失败时只能说「实现已完成，验证未通过」，不能说「完成」。
- 修复后只重跑失败的检查项和用例，不删除原始失败记录。
- PLAN.md 中必须包含「理解确认」环节，在开发前把 AI 对关键概念的理解显式化供用户确认；理解被纠正后必须重写受影响的计划部分。
- TEST_CASES.md 每条用例必须指定「验证方法」（jest / Playwright DOM / Playwright CSS / Playwright 交互 / API 对比 / 人工），验证时按指定方法执行。
- 验证流程的完整定义见 `shared/WORKFLOW.md` 的「15) 完成前验证」章节与「验证循环」；性能阈值依据见 `shared/PERFORMANCE.md`。（不存在独立的 `test-engineer` 技能，早期引用已废弃。）

## 性能门禁

性能是开发阶段门禁，但**按流程等级分流，且只在生产构建产物上判定**。完整依据、阈值数值、测量步骤见 `shared/PERFORMANCE.md`（唯一数值源，本文件不再重复抄阈值，避免双源冲突）。

核心规则：

- **分级执行**：L1 不跑性能；L2 默认只做「工程化检查清单」并记录，仅当改动涉及首屏/渲染链路/重依赖时才必须量化；L3 必须量化。
- **测量对象**：性能量化**只在生产构建产物（`npm run build` 后 serve `dist`）上做**，用桌面 preset、无网络节流。**dev server 数据只作风险参考，不作门禁判定**。
- **指标语义**：LCP 不作硬门槛（B 端主内容受后端响应支配）；硬约束是「骨架屏/壳层先出、主数据区不白屏」+ 首屏首包体积预算。
- 涉及 UI 的需求**都要过** `PERFORMANCE.md` 第 6 节「工程化检查清单」，这是不依赖 dev server 的兜底，不能跳过。
- **运行时性能与内存同等重要（监控产品重点）**：大列表虚拟化、图表增量 `setOption`、避免无谓重渲染、高频交互响应预算见 `PERFORMANCE.md` 第 3 节；实时刷新/长停留页面的定时器/订阅/监听/图表实例必须在卸载时清理（防内存泄漏）见第 4 节；涉及大数据渲染必须用接近生产的数据量验证见第 7 节。
- 无法跑生产构建/Lighthouse 时：`VERIFY.md` 标注「性能未量化」并完成工程化检查清单，列出风险点。
- 该量化却未达及格线时，不能输出「可以提测」，只能说「实现已完成，性能未达标」。
