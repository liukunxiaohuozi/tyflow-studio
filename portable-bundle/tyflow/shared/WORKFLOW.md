# 前端 AI 工作流执行版

## 目标定位

这是一套给前端内部使用的对话式开发工作流。目标不是“生成代码”，而是把一次需求从接收、分析、设计、实现、联调、验证到复盘，串成一条可重复执行的流程。

核心原则：

- 先理解，再动手。
- 先找复用，再写新代码。
- 先验证，再宣布完成。
- 先沉淀，再进入下一轮。

## 单一入口

默认入口是 `tyflow-do`。
用户可以直接说：

- `帮我做这个需求`
- `目标项目是 xxx`
- `继续联调`
- `帮我验证一下`

AI 负责自动路由，不要求用户手动区分流程级别。

## 流程分级

### L1 轻量流程

适用：

- 小 bug
- 样式修正
- 小字段调整
- 小交互修改
- 不涉及接口语义和公共组件改动

必须做：

1. 接收需求
2. 识别项目
3. 执行修改
4. 做最小验证
5. 写轻量复盘

### L2 标准流程

适用：

- 普通页面需求
- 新接口接入
- 客户定制功能
- 常规页面改造
- 需要数据绑定和交互联动

必须做：

1. 接收需求
2. 头脑风暴与需求分析
3. 生成设计规格
4. 识别项目与页面模式
5. 搜索可复用组件
6. 编写计划
7. 生成验收测试用例
8. 人工确认计划和测试用例
9. 按计划执行
10. 做契约和联调校验
11. 完成前验证
12. 写复盘

### L3 严格流程

适用：

- 跨项目复用或复制组件
- 公共组件修改
- 高风险业务逻辑
- 多 agent 并行开发
- Git worktree 隔离开发
- 权限、导航、数据范围、复杂图表语义

必须做：

1. L2 全部步骤
2. 测试驱动开发
3. 请求代码审查
4. 接收代码审查
5. 必要时并行 agent
6. 必要时 worktree 隔离
7. 更完整的复盘沉淀

## 信任等级

流程等级（L1/L2/L3）按任务复杂度分级，信任等级按 AI 自主程度分级。两者独立使用。

### 等级定义

T0 - 仅提供信息：

- AI 只分析、检索、建议
- 所有执行决策由人工做出
- 适用：新项目首次接入、不确定需求、首次使用工作流

T1 - 建议后确认：

- AI 给出具体建议和方案
- 人工确认后才执行
- 适用：标准需求开发

T2 - 自主执行，事后审核：

- AI 自主完成执行
- 人工在关键节点审核
- 适用：重复出现的同类需求，AI 建议已被验证过

T3 - 自主执行：

- AI 全流程自主完成
- 只在完成前验证阶段做人工检查
- 适用：高度标准化的需求（如已知页面的同类改造）

### 默认信任规则

不同操作有不同的默认信任等级：

| 操作 | 默认等级 | 说明 |
|------|---------|------|
| 组件检索和分析 | T2 | 检索结果可以被信任，但复用方式建议确认 |
| 页面结构和布局生成 | T1 | 生成建议后确认再执行 |
| 样式实现 | T2 | 按项目已有模式实现，不需要逐个确认 |
| 字段映射 | T1 | 必须确认，字段语义错误影响业务 |
| 接口联调 | T1 | 字段含义不确定时降为 T0 |
| 公共组件修改 | T0 | 必须人工全部决策 |
| 跨项目组件复制 | T0 | 必须人工全部决策 |
| 国际化包裹 | T2 | 按规则执行，验证时检查 |

### 信任提升规则

信任等级可以随需求迭代提升，但不能自动提升：

- 同类需求连续 2 次以上 AI 建议被采纳且验证通过，该类操作可提升一级
- 提升建议在 RETRO.md 中提出，由人工确认后生效
- 出现失效模式中的问题时，对应操作降回 T0 或 T1
- 不同操作的信任等级独立，不一起升降

## 阶段 0 · Open Design（可选，推荐）

设计探索与工程开发分两个环境，中间靠 `OD_HANDOFF.md` 交接。Open Design 项目目录在 OD 数据区（`Open Design/.../projects/<uuid>/`），**不在** `.tyflow` 内；Tyflow 只存路径索引（`OD_SOURCE.md`），不复制 HTML 原型。

```text
PRD / 需求 → Open Design 出 screens/*.html + DESIGN.md
           → OD_HANDOFF.md（designStatus: approved）
           → Tyflow 读 HANDOFF → L2 标准流程
```

### 何时新建 OD 项目 vs 迭代

| 场景 | 新建 OD 项目 | 新建 Tyflow 需求 |
|------|-------------|-----------------|
| 新模块 / 新页面组 / 新仓库 | ✅ | ✅ |
| 同需求改布局、加一屏、修交互 | ❌ 升 handoffVersion | ❌ |
| 大方向推翻且需保留旧方案 | ✅ v2 项目 | 视情况 |

**门禁：** `designStatus !== approved` 时，Tyflow 最多做到 PLAN + TEST_CASES，**禁止写业务代码**。

### OD 与 Tyflow 对应关系

```text
1 Tyflow 需求  ↔  1 OD 项目  ↔  1 OD_HANDOFF.md
Tyflow requirements/<id>/OD_SOURCE.md  →  指向 OD 项目路径
```

模板：`shared/templates/OD_HANDOFF.template.md`（P0 极简）、`OD_HANDOFF.full.template.md`（P0+P1 完整）。

## 主流程

### 1) 接收需求

输入可以来自：

- **Open Design 原型 + `OD_HANDOFF.md`**（设计定稿后的**首选**输入，优先级高于 PNG/Figma 截图）
- PRD
- Figma
- 截图
- 口头描述
- 接口文档
- cURL
- 线上问题描述

输出要求：

- 明确目标
- 明确项目
- 明确页面范围
- 明确验收标准
- 明确待确认问题

输入数据质量检查：

在进入下一步之前，检查输入材料的最低质量标准。质量不达标时必须提示补充，不能带着模糊信息往下推进。

PRD 最低标准：

- 有明确的页面目标（不只是"做一个 XX 页面"，而是"用户在这个页面上完成什么"）
- 有页面范围界定（做哪些、不做哪些）
- 有可量化的验收标准

Figma 最低标准：

- 有完整的设计标注（间距、字号、颜色）
- 有交互说明（点击后跳转/抽屉/弹窗/筛选）
- 有状态变体（空态、加载态、错误态、禁用态，至少有其一）

接口文档最低标准：

- 字段含义明确（不只是英文名，要有中文说明）
- 标注了必填/选填
- 有响应结构示例

截图/口头描述最低标准：

- 能明确看出改什么、改成什么样
- 如果无法从输入中提取验收标准，必须追问

Open Design / `OD_HANDOFF.md` 最低标准：

- `designStatus: approved`（未 approved 禁止进入 PLAN 确认后的开发）
- `screens` 表与真实 `screens/*.html` 一一对应
- `acceptance` 每条带 `odRef`（DOM 选择器或 `data-od-id`）
- `componentMap` 预填复用决策（reuse / project-wrapper / local-adapt / new-local）
- `tokenMap` 标注 must-match / allow-deviation / use-project-default
- `interactions` 含 loading / empty / error 三态

来源含 OD 时的读取顺序：

1. 需求目录 `OD_SOURCE.md` 或用户给出的 `OD_HANDOFF.md` 路径
2. `OD_HANDOFF.md` 全文
3. OD 项目 `screens/*.html`（对照交互与 odRef）
4. PRD / Figma / PNG（HANDOFF 索引，只读参考；**验收以 OD 原型 + acceptance 为准**）

从 HANDOFF 映射 Tyflow 产物：

- `meta` + `scope` → `REQUIREMENT.md`
- `screens` + `userFlows` + `interactions` → `SPEC.md`
- `componentMap` + `referencePages` → `COMPONENT_SEARCH.md`（预填，仍需代码库验证）
- `acceptance` → `TEST_CASES.md` + `VERIFY.md` 设计还原度
- `dataContracts` → `CONTRACT.md` / mock / 后续 api-contract 三件套

质量不达标时：暂停，回 Open Design 补原型或更新 HANDOFF，**不得用 PNG 猜测交互**。

质量检查不通过时：

- 列出缺失项
- 给出默认处理建议
- 对影响业务语义的缺失项暂停等待补充
- 对不影响整体流程的缺失项允许标注后继续

### 2) 头脑风暴

先把需求想清楚，再写代码。

必须输出：

- 页面目标
- 用户路径
- 关键状态
- 潜在复用点
- 风险点
- 待确认项
- 默认方案建议

如果需求还不清楚，必须暂停并向人工确认，不要边写边猜。

### 3) 生成设计规格

把模糊需求转成可执行、可验收的规格。L2/L3 中 `SPEC.md` 是开发真源：`REQUIREMENT.md`、PRD、截图、Figma、Open Design、口头补充都是输入源；进入开发后，代码实现、测试用例和验证结论必须追溯到 `SPEC.md`。如果输入材料与 `SPEC.md` 冲突，先修订 `SPEC.md`，不要绕过规格直接改代码。

`SPEC.md` 至少包含：

- 规格元信息（specVersion / status / updatedAt / source）
- 页面目标
- 用户路径
- 页面结构
- 交互规则
- 数据来源
- 接口依赖
- 状态说明
- 验收标准
- 明确不做的内容
- 稳定 Spec ID（如 `S-FUNC-001`、`S-DATA-001`、`S-STATE-001`）
- Traceability 初始表（Spec ID → 实现位置 → 测试用例 → 验证证据 → 状态）
- Change Log（规格变更、影响范围、是否需要重审计划/用例）

Spec 变更规则：

- 需求目标、页面范围、交互、字段语义、验收标准、接口契约、状态模型发生变化时，必须先更新 `SPEC.md`。
- `SPEC.md` 变更后，必须同步检查并更新 `PLAN.md`、`TEST_CASES.md`、`CONTRACT.md` / `INTEGRATION.md`（如涉及接口）和待验证项。
- 任何影响范围、验收标准、字段语义、组件复用决策或实现路径的 Spec 变更，都必须回到计划审查门禁，重新获得人工确认后才能继续开发。
- 不影响业务语义的小修正文案、错别字、格式说明可记录到 Change Log 后继续，但仍要确保 Traceability 不断链。
- 开发中出现“需要顺手补一个规格外能力”的想法时，必须先新增或修改 Spec ID，再评估是否重审计划；没有 Spec ID 的需求外实现不得落代码。

### 4) 识别项目

必须判断：

- 目标仓库
- 技术栈
- 路由结构
- 组件库使用方式
- 样式体系
- 相似页面
- 构建和测试命令
- 当前约束和风险

**识别到目标项目后，必须先读对应的项目级错题本 `shared/projects/<project>/LESSONS.md`**（不存在则按 `shared/projects/README.md` 新建），把其中与本次需求相关的条目当作本次开发的硬约束，避免重犯历史上已被纠正过的错误。

**同时必须按观云知识库开发**：开发前先读 `baseline/观云 知识库/knowledge-base-entry.md`，按其「任务路由」表，根据本次任务类型（页面开发 / 接口接入 / 样式还原 / 组件选型 / 发版打 Tag 等）只读 1–2 份最相关专题（`engineering/`、`design/`、`components/`），不要整库加载。后续实现、样式、请求服务层、分支与发版都必须符合知识库规范。冲突时按知识库的优先级裁决：**目标仓库真实代码 > 用户当前指令/项目输入（PRD/Figma/联调约束）> 知识库**。

### 5) 搜索可复用组件

搜索范围：

- 当前项目
- 已接入项目
- 跨项目业务组件
- 公共组件
- shared 工具函数
- service / contract / mock 结构

输出要求：

- 直接复用
- 本地改造
- 只参考不复用
- 源追踪复制
- 不复用

规则：

- 先增量扫描当前项目，再看已接入项目
- 目标项目中已有同类页面、同类组件、同名组件引入、局部二次封装或业务封装时，优先仿照目标项目真实用法
- 仿照范围包括 import 路径、外层容器、样式类、字段转换、ref 使用、缓存命名、空态/加载态处理
- 如果目标项目有二次封装，优先使用二次封装；不要绕过封装直接引入组件库原始组件，除非能说明封装不适用
- 只有目标项目没有真实用法或二次封装时，才按 shared registry / 组件库源码中的原始方式接入
- 复用判断必须记录最终采用：仿照项目用法 / 使用项目封装 / 使用组件库原始方式 / 新写局部组件
- 组件索引通过直接搜索代码库获取（Glob/Grep/Read），不依赖预填充的索引文件
- 组件搜索结果记录到需求目录的 `COMPONENT_SEARCH.md`
- 如果项目结构、依赖发生显著变化，必须重新搜索确认

### 6) 编写计划

把规格拆成可执行步骤。编写计划前，必须先把 AI 对需求中关键概念的理解显式化，供用户确认。

**先规划再开发是强制门禁，不是建议。** 涉及页面/模块/组件开发的需求（L2/L3）在写代码前**必须**先产出 `PLAN.md` 并经人工确认；没有计划不许动业务代码。

`PLAN.md` 至少包含：

- 理解确认（见下方）
- 任务拆分
- 每个计划步骤的稳定 ID、覆盖的 Spec/需求 ID，以及预计修改的文件或 glob 范围 `expectedFiles`；范围必须足够具体以识别计划外改动
- **模块复用决策（强制）**：把本次涉及的每个模块/区块逐条列出，明确归类为以下之一并写依据：
  - `复用现成组件`：直接用 `@ty-sdk/components` 或项目已有组件（写明组件名 + 来源）
  - `使用项目二次封装`：用目标项目已有的本地封装（写明封装位置）
  - `本地改造`：基于现成组件改造（写明改什么、为什么）
  - `新封装`：现有都不适用，需要新写（**必须说明为什么不能复用**）
- 依赖关系
- 串行/并行划分
- 风险任务
- 验证步骤
- 是否需要 TDD
- 是否需要 worktree
- 是否需要 code review

理解确认：

- 把需求中的每个关键概念（页面类型、交互模式、组件选型、数据结构、业务规则）的 AI 理解写出来。
- 理解确认不是复述需求，而是暴露 AI 的理解偏差——比如「列表页」在你脑子里是带筛选条件的可配置列表，AI 可能理解成简单表格。
- 用户审查计划时，先确认理解是否正确，再审查任务拆分。
- 理解被纠正后，必须重写受影响的计划部分，不能只在理解确认表里改文字。

### 7) 生成验收测试用例

根据需求文档、`SPEC.md` 和 `PLAN.md` 生成 `TEST_CASES.md`，把验收标准前置。

`TEST_CASES.md` 至少包含：

- 验收范围
- 功能用例
- 交互与状态用例
- 数据与接口用例
- 异常与边界用例
- 国际化用例
- 设计还原度用例（有设计稿时）
- 回归风险用例

规则：

- L2/L3 进入开发前必须生成 `TEST_CASES.md`。
- 测试用例必须覆盖需求文档中的验收标准和 `SPEC.md` 中的关键状态；每条 P0/P1 用例必须引用对应 Spec ID。
- P0/P1 用例必须在开发完成后执行；未执行不得宣布完成。
- 如果生成测试用例时发现需求缺口，回到需求澄清或 SPEC 修订。
- 如果人工修改需求、计划或测试用例，必须同步更新 `TEST_CASES.md` 后重新确认。
- 如果发现某个 Spec ID 没有测试用例，必须补用例或在 `TEST_CASES.md` 明确说明为什么只能人工确认；不能静默跳过。

计划审查门禁：

- L2/L3 必须在进入开发前完成人工审查。
- 审查内容包括任务拆分、改动范围、风险点、验证方式、是否需要 TDD、是否需要 review、测试用例是否覆盖需求、是否还有待确认业务语义。
- 人工未确认 `PLAN.md` 和 `TEST_CASES.md` 前，不允许进入执行计划，不允许开始改代码。
- 输出 `PLAN.md` 和 `TEST_CASES.md` 后必须停下来询问：是否可以按此开发计划和测试用例开始开发？
- 收到人工明确确认前，只能继续解释、修订或补充计划和测试用例；不能修改业务代码。
- 如果人工修改计划或测试用例，或要求 AI 辅助修改，修改完成后必须再次发起确认，直到人工明确同意按最新版计划和测试用例开发。
- 有效确认必须是明确授权，例如“可以”“确认”“按这个计划开发”“开始开发”。沉默、泛泛讨论、只确认某个局部点，不算通过。
- 如果审查发现需求、接口、组件复用或业务语义仍不清楚，回到对应步骤补齐后重新审查。

### 8) 执行计划

执行时必须按计划推进，不跳步。

要求：

- 开始执行前确认 `PLAN.md` 和 `TEST_CASES.md` 已通过人工审查，并且用户已经明确授权按最新版计划和测试用例开始开发。
- 开始执行前确认 `SPEC.md` 状态为 `confirmed`，且 `PLAN.md`、`TEST_CASES.md` 引用的是同一版 `specVersion`；如果规格版本不一致，先同步产物并重新确认。
- 每做完一步就做局部验证
- 优先复用已有组件和页面模式
- 不为了图快跳过契约和联调
- 不把”看起来能用”当作完成
- 开发过程中所有出现的汉字，必须先用 `I18nT(...)` 包裹，再继续实现

AI 决策追溯要求：

执行过程中以下决策必须记录到 PLAN.md 的”AI 决策追溯”表：

- 组件选择：选了什么组件、为什么选、排除了什么、是仿照项目用法还是新写
- 字段映射：映射规则是什么、依据来源是文档还是猜测、是否经过人工确认
- 偏离计划：偏离了 PLAN.md 的哪些步骤、偏离原因、是否有替代方案、是否经过确认
- 复用判断：最终采用直接复用/本地改造/参考/复制/新写，判断依据是什么
- 规格变更：新增/修改/删除了哪些 Spec ID，影响哪些实现、测试和验证项，是否已重新确认

不要求每个小决策都记，但影响页面结构、数据流、交互行为或接口绑定的决策必须记。

### 8b) 测试驱动开发（条件触发，与 Step 8 并行）

适用范围：

- 数据转换
- service 字段映射
- 图表 option 生成
- 复杂筛选、排序、分页
- 权限和状态流转
- 已经反复出错的逻辑

规则：

1. 先写失败测试
2. 再写最小实现
3. 测试通过后再重构

### 9) 契约校验

当页面要接真实数据时，先做契约确认。

必须确认：

- 请求方法
- 字段名
- 字段类型
- 默认值
- 空值行为
- 错误结构
- 加载态和空态

TypeScript 类型门禁：

- 所有新增或修改的请求参数和响应结构，必须先定义 TypeScript 类型（interface / type），再写业务逻辑。
- 类型定义放在与 service 同级的 `types.ts` 或内联到 service 文件头部，不要散落在页面组件中。
- 进入实现前，`CONTRACT.md` 必须包含完整的请求/响应类型定义。
- 类型定义就是契约的代码化表达；实现过程中发现类型与实际不符时，先修正类型再改业务。

契约分两层（命名即身份）：

- UI 契约 `XxxVO` / `XxxModel`：页面消费、稳定，由"页面要展示什么"决定；后端响应 `XxxResp` / `XxxDTO`：易变，仅 service 内部使用。
- **单一映射点**：后端 → UI 契约的映射只写在 service 的 `mapToXxx`，页面/组件禁止字段重命名/兜底/转换；后端原始类型不得流到页面。
- **后端未给接口定义不阻塞**：按"页面要展示什么"自定 UI 契约 + 自造 mock 先开发，接口到位后只补 service 映射这一步，页面不返工。
- 详细规范见 `baseline/观云 知识库/engineering/request-and-service.md` 的「契约层可定位性规范」。

输出到 `CONTRACT.md`。

### 10) 是否联调

页面和契约完成后，询问是否进入联调。

联调输入优先级（取能拿到的最高一档，每一档都不阻塞开发）：

1. 接口文档（带字段中文含义）+ 真实响应样例 —— 最佳
2. 真实响应样例 / **浏览器抓包**（用 `ide-browser` MCP 在已登录页面抓 Network，token 留在浏览器，不进对话）—— 次佳
3. cURL —— 仅从中提取结构信息，不据此盲调
4. 都没有 —— 用自定 UI 契约 + mock 先开发，接口到位再补 service 映射

规则：

- 只提取联调需要的结构信息（顶层壳、字段、枚举、分页结构）
- **优先浏览器抓包获取真实数据**，避免在脆弱的终端环境盲调接口
- 原始 cURL / token / cookie / 私密头**不进对话上下文、不落盘**
- 调不通时说明阻塞点，**绝不静态硬猜接线**；改用样例/抓包，或回退 mock 继续
- 只写脱敏后的映射和验证结果

### 11) 自主联调

联调环境默认为 dev。

联调阶段只改 service / 映射，不随意改页面 DOM、样式和交互。

映射只写在 service 的 `mapToXxx`（唯一映射点），逐字段注释来源（对应 `INTEGRATION.md` 条目）；关键字段加 shape 漂移检测，让后端结构变化在 service 层暴露（带模块名 + 缺失字段），而不是页面静默崩。

联调具体操作流程：

1. 先调主接口（页面核心数据的接口），再调辅助接口（下拉选项、字典值、用户信息等）
2. 多个接口有依赖关系时（比如列表接口的参数依赖详情接口的返回），先调被依赖的接口
3. 带参数的接口（分页、筛选、排序、时间范围）必须用真实参数调一次，不能用默认值凑合
4. 接口返回 401/403 时暂停，提示用户检查认证状态，不自行修改认证逻辑
5. 接口返回 500 或超时时暂停，记录错误信息，不自行绕过

接口返回和 contract 不一致时的处理规则：

- 返回多了字段：service 层忽略多余字段，不影响页面
- 返回少了字段：检查是否是核心字段，核心字段缺失暂停确认，非核心字段用默认值兜底并记录
- 字段类型不一致：暂停确认，不自行强转
- 嵌套结构变化：暂停确认，不自行改 contract

字段变更分级（应对后端结构漂移）：

- **非契约级**（改名 / 挪层级 / 换枚举值 / 加包装壳）：只改 service 的 `mapToXxx` 一处，页面/组件/contract 不动。绝大多数后端漂移属此类。
- **契约级**（页面要展示的内容真的增减/改变）：属真需求变更，才动 contract 和页面，并回到计划确认。
- 处理后跑 mapper 单测 + 页面在浏览器验证，并更新 `INTEGRATION.md` 映射表。

联调完成判定：

只有同时满足以下条件，才能说"联调完成"：

- 所有核心接口至少调通一次，返回数据能正确渲染到页面
- 字段映射全部已确认，没有"待确认"状态的映射
- 错误态、空态、加载态至少触发过一次真实场景（不是只看 mock）
- 分页/筛选/排序等交互操作经过真实接口验证
- 接口返回的异常情况（空数据、超长字段、特殊字符）已在 service 层处理

联调回滚机制：

联调过程中遇到以下情况时，可以回退到 mock 数据继续开发：

- 后端接口尚未开发完成，联调无法继续
- 接口存在 bug 需要后端修复，且修复周期不确定
- dev 环境不稳定，接口频繁不可用

回滚规则：

- 回退到 mock 时不删除 service 层已写好的映射代码，只切换数据源
- 在 INTEGRATION.md 中记录回滚原因、已确认的映射、待后端修复的问题
- 页面其余功能（样式、交互、非联调逻辑）继续开发和验证，不被接口阻塞
- 后端修复后重新进入联调时，从上次断点继续，不需要从头开始

如果出现以下情况，必须暂停并人工确认：

- 字段含义不明确
- 多个字段都可能绑定到同一个 UI
- 接口返回结构和文档不一致
- 需要改业务语义

### 15) 完成前验证

#### 验证执行模式路由

Tyflow 保留完整原生验证能力，但先根据调用上下文选择执行模式：

- `standalone`（默认）：未收到外部编排标识时，完整执行本节原生验证循环。只有 Tyflow、没有 Studio 或外部测试 Skill 的机器必须走此模式，能力和准入标准不得降级。
- `orchestrated`：只有调用方明确声明后续会执行正式测试，并提供当前代码快照、已确认计划和测试用例时才启用。开发阶段只做实现所需的低成本局部反馈检查，不运行完整完成前验证、不生成最终 `VERIFY` 结论、不声称可提测；正式结论等待编排器返回的测试结果。

外部测试结果只有在代码快照、计划版本/哈希、必测用例和证据全部匹配时才可复用。不匹配、缺失或不可信时，回退到 `standalone` 完整验证。外部结果仅覆盖部分范围时，缺口必须补测，不能把部分结果冒充完整通过。

声称完成前，必须跑验证。**完整的提测准入门、三层验证边界、测试密度矩阵、B 端专属用例见 `shared/VERIFICATION.md`**；下面的验证循环是其执行顺序，`VERIFY.md` 按准入门逐项打勾。验证按固定顺序执行，任何一步失败都不得继续往下。

两条贯穿原则（先读）：

1. **增量基线对比（解决历史债务阻塞）**：tsc 和 eslint 不要求「全量零错误」，而是要求「**本次改动不新增错误**」。做法：在动手前对目标项目跑一次基线（记录既有 tsc 报错数/eslint 报错数到 `VERIFY.md` 的基线栏），改完后再跑一次，**只对「新增的错误」卡门**。既有历史债务（如 `@types/d3-dispatch`、`TopoContext.ts`）允许存在但**不允许因本次改动增加**。这样门禁既不被历史债务永久阻塞，也不放过本次引入的问题。
2. **按 L 级别分流（避免门禁过重被绕过）**：
   - **L1**：只跑 ①增量 tsc + ②增量 eslint（若改了 `utils` 等纯逻辑仍需补 ③单测）；④–⑧按需，可在 `VERIFY.md` 说明跳过原因。
   - **L2**：① ② ③ ④ ⑤ ⑥ 必做；⑦ ⑧ 按 `PERFORMANCE.md` 第 1 节判定（涉首屏/重依赖才量化，否则做工程化检查清单并记录）。
   - **L3**：① – ⑨ 全做，性能必须量化。

验证循环：

```
① TypeScript 编译（增量基线：本次不新增 tsc 错误）
  │ 新增错误 → 修复 → 重跑①
  ▼ 无新增
② ESLint（增量基线：本次不新增 eslint 错误）
  │ 新增错误 → 修复 → 重跑②
  ▼ 无新增
③ 单元测试（jest）
  │ 失败 → 修复 → 只重跑失败用例
  ▼ 通过
④ 构建（npm run build）
  │ 失败 → 修复 → 重跑④
  ▼ 通过
⑤ 按 TEST_CASES.md 逐条执行 P0/P1 用例
  │ 失败 → 修复 → 只重跑失败用例
  ▼ 全部通过
⑥ 需求覆盖度检查（REQUIREMENT.md 逐条对照）
  │ 未覆盖 → 补实现 → 回到⑤
  ▼ 全部覆盖
⑦ Playwright 页面验证（L3 或涉首屏交互时）
  │ 失败 → 修复 → 只重跑失败项
  ▼ 通过或按级别跳过
⑧ 性能验证（按 PERFORMANCE.md：仅生产构建产物 + 桌面无节流；涉首屏/重依赖才量化）
  │ 不达标 → 分析瓶颈 → 修复 → 重跑⑧
  │ 不涉首屏 → 做工程化检查清单 → 记录到 VERIFY.md
  ▼ 达标 / 清单通过 / 风险已记录
⑨ 输出 VERIFY.md（含所有原始证据 + 基线对比栏）
```

验证内容视任务而定：

- 构建
- 类型检查
- 单元测试
- 按 `TEST_CASES.md` 执行验收用例
- 页面检查
- 样式检查
- 接口数据验证
- 图表数据绑定
- 空态和错误态
- 国际化扫描和校验
- 性能影响检查
- 可观测性检查

性能影响检查至少包括：

- 不要为了优化性能而改变业务逻辑，避免引入新 bug。
- 不要在没有 review 的情况下合入代码。
- 检查新引入的组件是否是懒加载或按需加载。
- 检查是否误把重依赖同步引入首屏。
- 检查首屏、交互和接口返回慢时是否会出现白屏。
- 对有明显加载风险的页面，必须引入骨架屏或等价占位。
- 骨架屏的结构要按模块对应页面布局，哪个模块会出现，骨架屏就要呈现哪个模块的结构。
- 若修改涉及首屏性能，必须回看渲染链路，确认没有把原本延后的内容提前同步执行。
- 如果性能优化和业务逻辑冲突，优先保证业务正确，再做性能分解。

性能指标门禁：**完整阈值、测量方式、分级规则统一见 `shared/PERFORMANCE.md`（唯一数值源）。** 要点：

- 按 L 级别分流（L1 不跑 / L2 条件性 / L3 必跑），判定标准：是否触碰首屏、渲染链路或重依赖。
- 量化**只在生产构建产物上做**（桌面 preset、无节流）；dev server 数据仅作风险参考。
- LCP 不作硬门槛；硬约束是「骨架屏先出、主数据区不白屏」+ 首屏首包体积预算。
- 涉及 UI 的需求都要过 `PERFORMANCE.md` 第 6 节工程化检查清单。
- 该量化却不达及格线时不能输出「可以提测」。

可观测性检查至少包括：

- 新增组件是否有错误边界（ErrorBoundary 或等价机制）。
- 关键交互是否有性能标记（可被 APM 采集，如页面加载、接口调用、渲染耗时）。
- 异步操作是否有错误处理和加载状态追踪。
- 图表和表格是否有空态、加载态、错误态的完整处理。
- 新增页面是否已接入项目的监控埋点（如有）。

可观测性不是收尾补丁，开发过程中就要保证新代码具备可被观测的能力。（提测准入门与详细判定见 `shared/VERIFICATION.md` 第 6c 节。）

设计还原度检查（有 Figma、设计稿或 **Open Design 原型** 时必须做）：

**基准优先级：** OD 原型 + `OD_HANDOFF` acceptance / tokenMap > Figma > PNG。

有 `OD_HANDOFF.md` 时额外要求：

- 逐条执行 `acceptance`（引用 `odRef`），结果写入 `VERIFY.md`
- `tokenMap` 中 must-match 项对照实现页 computed style 或项目 design token
- `VERIFY.md` 必须列：`handoffPath`、`handoffVersion`、逐条 acceptance 结果
- 打开 OD `screens/<对应屏>.html` 与实现页并排对照布局与交互

- 页面整体布局是否和设计稿一致（左右结构、上下分区、宽高比例）
- 关键间距、字号、颜色是否对齐（允许 1-2px 偏差，不允许明显差异）
- 表格列宽、表单项排列、按钮位置是否和设计稿一致
- 图表类型、配色、图例位置是否和设计稿一致（数据可以用 mock，但图表结构必须对）
- 交互状态是否覆盖了设计稿中的所有变体（默认、hover、active、disabled、选中、展开/收起）
- 弹窗/抽屉/下拉的尺寸和位置是否和设计稿一致
- 响应式断点下的表现是否合理（如果设计稿有响应式设计）

没有设计稿的需求跳过此检查，但要在 VERIFY.md 中注明”无设计稿，跳过设计还原度检查”。

验收用例检查：

- `VERIFY.md` 必须引用 `TEST_CASES.md` 中的用例 ID。
- P0/P1 用例必须全部执行，并记录通过/失败/阻塞。
- P2 用例如未执行，必须说明原因和剩余风险。
- 测试用例失败时不能写”完成”；必须修复后重新验证，或明确标记为阻塞。

需求覆盖度检查：

- 回溯 `REQUIREMENT.md` 中列出的所有需求条目（页面范围、验收标准、待确认问题），逐条对照实际代码改动和测试结果。
- 每条需求条目标记为：已覆盖 / 部分覆盖（说明缺失内容） / 未覆盖（说明原因） / 已变更（说明变更来源和新范围）。
- 存在”未覆盖”或”部分覆盖”的核心需求时，不能宣布完成。
- 验证结果写入 `VERIFY.md` 的需求覆盖度章节。

验证失败不能写”完成”。

### 16) 国际化规则

国际化是默认门禁，不是收尾补丁。

要求：

- 开发过程中所有中文文案都要先用 `I18nT(...)`
- 不要直接把中文硬写进新增 JSX、配置、提示语和按钮文案
- 不要每新增一处中文文案就执行 `npm run scan`
- 等静态页面结构和主要文案集中完成后，再统一执行一次 `npm run scan`
- `npm run scan` 执行后，系统会把 `I18nT` 包裹内容扫描到 `src/locales/en-US.json` 和 `src/locales/zh-CN.json`
- 其中 `src/locales/en-US.json` 里 value 仍为中文的项，必须在交付前翻译成英文
- **`grep` 扫硬编码中文只用于「找遗漏」，不能替代 `npm run scan`**：前者找漏包裹的中文，后者确认 key 正确写入 locale 产物——两步分工不同，缺一不可，不要用 grep 通过冒充 scan 通过
- **`npm run scan` 是验证流程的固定一步**：提测前必须实际执行并粘贴命令输出，不能因为它"排在跑测试之前"就跳过；未跑 scan / 未确认产物，国际化门禁不算通过
- **国际化通过 = 三条件齐全**：全部中文已 `I18nT` 包裹 + `npm run scan` 已跑 + `en-US.json` 无残留中文。测试中发现未包裹的中文或 `en-US.json` 残留中文即判未通过，按「补包裹 → 重跑 scan → 翻译 → 复核」闭环处理后才算通过（完整判定见 `VERIFICATION.md` §2c）
- 只允许保留少量确实无法即时翻译、且已经标记的待处理项

### 17) 完成分支处理

任务结束后，只能四选一：

- 合并到目标分支
- 提 PR（PR 描述必须含测试报告摘要：用例场景计数 / 覆盖率声明 / 跳过项 / 关键证据可复现命令 / 难自证项确认状态，写入前脱敏；见 `VERIFICATION.md` 第 2b 节）
- 保留当前分支继续观察
- 丢弃实验性改动

### 18) 复盘沉淀

必须记录：

- 耗时
- 实际问题
- 有效修复
- 可复用经验
- 可沉淀到 shared 的规则
- 效果度量指标（至少 3 项）
- 知识库健康度检查结果
- 信任等级调整建议

输出到 `RETRO.md`。

**收尾动作（不可省略）**：复盘完成后，把本次效果度量追加为 `shared/METRICS.md` 需求度量表的一行。单个 RETRO 的指标是孤立的，只有汇总到 METRICS.md 才能形成基线、看趋势、向团队证明工作流是否真的提效。

沉淀分流规则：

- 自动纳入：已经验证通过、适用范围清楚、无敏感信息、不会改变业务语义的流程性经验，可以直接写入对应 shared 文件。
- 建议确认：影响团队长期行为、公共组件、接口语义、权限、导航、数据范围、跨项目复制策略的经验，只能提出建议，等待人工确认后再写入 shared。
- 仅本需求记录：只适用于当前需求、依赖临时环境、证据不足、字段含义未确认或带有敏感上下文的经验，只留在当前 `RETRO.md`。

沉淀目标选择：

- 稳定规则、门禁、禁止事项（**全局通用、跨项目成立**）写入 `shared/RULES.md`。
- **只对某个项目成立**的反复纠正、踩坑、字段/接口语义、构建与测试坑，写入 `shared/projects/<project>/LESSONS.md`（门槛：同类问题重复 ≥ 2 次，或明显容易复犯）。这是「项目特定经验」的正确归宿——既不污染全局规则，又能让后续 AI 开发该项目前主动读到。
- 已确认的长期业务决策、信任等级调整、团队约定写入 `shared/DECISIONS.md`。
- 组件路径、复用方式、项目真实用法记录到需求目录的 `COMPONENT_SEARCH.md`；长期有价值的经验可写入 `shared/registry/ty-sdk-components.md` 或 `baseline/component-selection.md`。
- 反复出错的代码行为优先沉淀为测试、lint、脚本或验证步骤；不要只写文档。
- 还不稳定但值得观察的经验留在需求目录，下一次同类需求再验证。

沉淀前检查：

- 是否经过本次验证证明有效？
- 是否能说明适用范围和不适用范围？
- 是否和已有规则或决策冲突？
- 是否包含 token、cookie、Authorization、未脱敏响应、客户敏感数据或本机路径？
- 是否应该由人工确认后再升级为 shared？

同类问题重复出现 2 次以上时，必须在 `RETRO.md` 明确提出规则化建议，并给出建议落点：全局通用 → `shared/RULES.md`；**项目特定 → `shared/projects/<project>/LESSONS.md`**；并据情况补测试用例或调整 `TRUST.md` 信任等级。

复盘时必须回看本需求的 `ATTEMPTS.md`：把**可复发的死路 / 行不通的方案**提炼成项目错题本 `LESSONS.md` 或规则；把**对工作流本身的反馈**确认后并入 `shared/FEEDBACK.md` 的处理。`ATTEMPTS.md` 是过程日志，留在需求目录即可，不必清空。

知识库健康度检查：

复盘时至少快速检查以下内容：

- 本次用到的组件是否和代码现状一致（路径、用法、状态）
- 本次用到的字段映射经验是否仍然有效
- 是否有规则在实际开发中被绕过或忽略
- 是否有重复出现的问题尚未沉淀为规则

检查方式：

- 不需要做全量扫描
- 只检查本次需求实际触碰到的索引和规则
- 发现问题的标记为 draft 或补充更新
- 无变化的确认 lastVerifiedAt

## 组件复用策略

默认策略：

- 先找当前项目
- 再找已接入项目
- 再看 shared/registry/ty-sdk-components.md 和 baseline/component-selection.md
- 能直接复用就不要复制
- 当前项目有真实使用方式时，优先跟随当前项目范式
- 当前项目有二次封装时，优先使用二次封装
- 当前项目没有用法时，才使用组件库原始接入方式

跨项目复制只在这些情况成立：

- 没有可依赖的公共组件
- 复用成本高于复制成本
- 目标项目和现有设计有明确差异
- 已经确认维护边界

### 图表规则

- 优先使用项目已有图表封装
- 没有封装再用 ECharts
- 不要把 Figma 图直接识别后用静态 SVG 画死
- 图表必须能与后端数据联调

### 首屏和渲染链路

首屏只保留最必要的内容：

- 顶部
- 查询入口
- 核心交互

以下内容尽量延后：

- 建议查询
- 结果图表
- 概览
- 追踪
- 原始数据
- 抽屉内容
- 大编辑器

原则：

- 先让页面可见
- 再让重块进场
- 先减少同步渲染
- 再考虑继续拆包

## 并行 Agent 与 Worktree

适用场景：

- 大需求
- 互不冲突的任务
- 组件搜索、契约分析、测试编写、代码审查可并行

规则：

- 每个 agent 边界要明确
- 不允许多人改同一批文件

## 门禁

### 国际化门禁

  开发过程中所有新写的中文文案都必须先用 `I18nT(...)` 包裹。不要每新增一处文案就运行 `npm run scan`；等静态页面结构和主要文案集中完成后，再统一执行一次 `npm run scan`，让扫描结果落到 `src/locales/en-US.json` 和 `src/locales/zh-CN.json`。其中 `src/locales/en-US.json` 里 value 仍为中文的项，必须在交付前翻译成英文。`grep` 找遗漏不能代替 `npm run scan` 确认产物；scan 必须实际执行并粘贴输出，否则国际化门禁不通过。

### 需求澄清门禁

  在需求没有理解清楚之前，禁止直接进入开发。

  必须先完成的动作：

- 梳理需求目标、页面范围、业务语义、接口边界和验收标准。

- 把不明确点明确列出，先发起讨论或人工确认。

- 对会影响页面行为、字段绑定、权限、导航、数据范围、公共组件复用结果的问题，必须先确认。
  
  允许进入开发的条件：

- 关键业务语义已经明确。

- 不确定点已经收敛，或者已明确采用哪一版默认方案。

- 当前需求已经可以写成可执行的 `SPEC.md`。

- L2/L3 已完成 `PLAN.md` 和 `TEST_CASES.md`，并且计划与测试用例已经通过人工审查。

- 人工已经明确授权按最新版 `PLAN.md` 和 `TEST_CASES.md` 开始开发。

### 开发边界（红线，任何等级都不得越过）

开发过程中遇到「理解不清」必须**立即停下、说明卡点、向人工提问，确认后再继续**，禁止自行假设推进：

- 需求 / 业务语义没看懂（要做什么、边界在哪、异常怎么处理）→ 停下问。
- 组件复用没判断清（有没有现成、复用还是封装、封装到什么粒度）→ 停下问。
- 接口字段没理解清（含义、映射、类型、枚举取值、空值/异常语义）→ 停下问。

红线行为，禁止触碰：

- 不猜需求、不猜字段含义。
- 不瞎写字段兼容 / 容错（用 `||`、可选链、默认值去「兜」一个自己没搞懂的字段＝掩盖问题）。
- 不为开发而开发、不加需求外的东西。
- 不重复造轮子（动手前先按 `PLAN.md` 的「模块复用决策」搜现成的）。
- 不「自以为可以这样」就把 UI 绑定到不确定的接口字段——**错误绑定会埋下难排查的 bug，或导致后续修改方向错误**。

必须做到：先思考、先理解业务、对本次需求负责；每个被绑定的字段都要有来源、转换规则和证据。宁可多问一句，不带着模糊往下写。
  
  ### 性能优化门禁

  性能不是收尾项，开发过程中就要一起校验。

  必须检查：

- 新引入的组件是否为懒加载或按需加载。

- 是否把原本可以延后的重依赖同步带进首屏。

- 页面在前端渲染慢、接口返回慢时是否会白屏。

- 是否需要骨架屏或等价占位。

- 骨架屏是否按模块布局对应页面结构，而不是随便画一个占位。

- 性能优化是否改变了业务逻辑或引入新 bug。

- 提交前是否已经 review 过关键改动。

  ### 性能指标门禁

  **完整阈值、测量步骤、分级规则统一见 `shared/PERFORMANCE.md`（唯一数值源，此处不再抄表，避免多处数值冲突）。**

  要点：

- 按 L 级别分流执行（L1 不跑 / L2 条件性 / L3 必跑），判定标准是否触碰首屏、渲染链路或重依赖。
- 量化只在**生产构建产物**上做（桌面 preset、无节流）；dev server 数据仅作风险参考。
- LCP 不作硬门槛；硬约束是骨架屏先出、主数据区不白屏、首屏首包体积预算。
- 涉及 UI 的需求都要过 `PERFORMANCE.md` 第 6 节工程化检查清单（不依赖 dev server）。
- 监控产品的**运行时性能**（大列表虚拟化、图表增量渲染、重渲染、高频交互响应预算）和**实时页内存泄漏**（定时器/订阅/监听/图表实例卸载清理）必须检查，详见 `PERFORMANCE.md` 第 3、4 节；涉及大数据渲染的需求必须用接近生产的数据量验证（第 7 节）。
- 该量化却不达及格线时不能输出「可以提测」。

### 跨浏览器兼容门禁

后续开发的页面、样式、交互**必须在 Chrome 和 Firefox 最新稳定版都正常**，不允许「Chrome 正常、切到 Firefox 样式错乱」。

- 提测前关键页面/交互在两个浏览器各实测一遍，附两端截图或说明（准入项见 `VERIFICATION.md`）。
- 主动规避高发差异：只带 `-webkit-` 前缀的属性要补标准属性 / Firefox 方案；滚动条用 `scrollbar-width`/`scrollbar-color` 而非 `::-webkit-scrollbar`；原生表单/日期控件、flex/grid 细节、`backdrop-filter` 等两端核对。
- 命中并解决的差异写入项目 `projects/<project>/LESSONS.md`，避免复犯。

### AI 失效模式

以下场景是前端工作流中 AI 最容易失效的地方。遇到这些模式时必须警惕：

#### 1. 模糊输入导致偏差

- 现象：PRD 或 Figma 不清晰，AI 按自己的理解填充细节，结果偏离意图
- 检测：SPEC.md 中出现 PRD 没有提到的功能细节
- 应对：回退到输入质量检查，补充材料后再推进

#### 2. 过度自动化

- 现象：AI 在信任等级不足时自行决定字段映射、组件选择或业务语义
- 检测：AI 输出被人工频繁覆盖（同一需求覆盖超过 3 次）
- 应对：降低该类操作的信任等级，改为建议模式

#### 3. 上下文丢失后继续执行

- 现象：对话压缩或中断后，AI 基于不完整状态继续开发
- 检测：新产出与 CURRENT.md 或已有产物矛盾
- 应对：强制读取 CURRENT.md 和最近产物后再继续

#### 4. 知识库污染

- 现象：错误的组件经验、过期的字段映射、未确认的规则被 AI 当事实使用
- 检测：AI 推荐的组件路径或用法在项目中不存在
- 应对：触发重新搜索代码库，更新 COMPONENT_SEARCH.md 和 baseline/component-selection.md

#### 5. 忽视项目范式

- 现象：AI 绕过项目二次封装直接引入组件库原始组件，或使用项目不存在的模式
- 检测：新代码的 import 路径与项目现有用法不一致
- 应对：回退到组件检索步骤，强制仿照项目真实用法

#### 6. 静态实现

- 现象：AI 把图表、表格、筛选做成了静态 JSX，不接真实数据
- 检测：组件内部没有 service 调用、没有状态管理、没有空态/错误态
- 应对：重做该部分，必须接入 mock 数据和状态管理

#### 7. 验证造假

- 现象：AI 声称验证通过但实际没有运行命令或检查页面
- 检测：VERIFY.md 中验证结果为空或只有"看起来没问题"
- 应对：必须附带验证命令输出或截图证据

**关键信号：当 AI 的输出被人工连续覆盖时，不是人的问题，是信任等级或输入质量的问题。**

## 每次执行前检查

每次用户说“继续”“继续联调”“验证一下”“修一下”时，先做恢复检查，再进入具体流程。

必须读取：

- `.tyflow/local/CURRENT.md`（活跃需求索引 + 当前默认需求）
- 对应的 `.tyflow/local/active/<requirement-id>.md`（该需求真实状态）
- 当前需求目录最近产物
- `.tyflow/shared/TRUST.md`（确认本次涉及操作的当前信任等级，决定哪些步骤可自主、哪些需人工确认）
- `.tyflow/shared/projects/<project>/LESSONS.md`（该项目错题本，回看历史已纠正过、易复犯的问题，避免重犯）
- `.tyflow/baseline/观云 知识库/knowledge-base-entry.md`（首次接手该项目或开发前，按任务路由读取相关专题；开发须遵循其工程/设计/组件规范）
- 目标项目 Git 状态
- 目标项目最近改动文件

必须判断：

- 当前需求 ID 是否存在（多个活跃需求时，先确认是哪一个，不要假设）
- 当前阶段是否明确
- 是否有未解决阻塞点
- 是否有用户或其他工具产生的新改动
- 继续执行是否会覆盖未确认改动
- 本次操作的信任等级是否允许自主执行（否则降级为「建议 + 等确认」）

如果状态不完整，按下面格式暂停：

```text
当前无法安全继续：
- 缺失状态：
- 已找到信息：
- 建议下一步：
```

**卡住需要找人工前，先记一笔 `ATTEMPTS.md`（目标 / 尝试 / 卡点 / 处置-待人工）再提问**，让人工一眼看懂已经试过什么；如果卡点是「工作流 / 门禁 / 规则本身行不通」，记到 `shared/FEEDBACK.md` 而不是 `ATTEMPTS.md`。

## 执行状态更新规则（支持多需求并行）

状态分两层，解决「单一 CURRENT.md 撑不住并行 agent / worktree」的问题：

1. **每个需求一个状态文件**：`.tyflow/local/active/<requirement-id>.md`。这是该需求的真实状态来源。并行进行的需求各有各的文件，互不覆盖。
2. **`.tyflow/local/CURRENT.md` 降为「活跃需求索引 + 当前默认指针」**：只维护一张表，列出当前所有活跃需求和它们的指针，并标出「当前默认需求」（用户说「继续」时默认指向它）。

每个 `local/active/<requirement-id>.md` 的最小内容：

```text
需求 ID：
流程等级：
当前阶段：
目标项目：
worktree/分支：（并行时必填，标明隔离边界）
已完成：
下一步：
阻塞点：
待确认：
最近验证：
更新时间：
```

`local/CURRENT.md` 的最小内容：

```text
# 活跃需求索引

当前默认需求：<requirement-id>

| 需求 ID | 流程等级 | 目标项目 | 当前阶段 | 状态文件 | 更新时间 |
|---------|---------|---------|---------|---------|---------|
| ... | L2 | explore | 联调中 | local/active/<id>.md | 2026-06-10 |
```

规则：

- 每完成一个阶段，更新对应的 `local/active/<id>.md`，并同步 `CURRENT.md` 索引行。
- 用户说「继续」且未指明需求时，操作 `CURRENT.md` 的「当前默认需求」；存在多个活跃需求时，先确认是哪一个，不要假设。
- 并行需求必须各自标明 worktree/分支边界；不允许两个活跃需求改同一批文件（见「并行 Agent 与 Worktree」）。
- 不允许只改代码、不更新状态文件。
- 不允许验证失败后把 `下一步` 写成完成。
- 如果代码状态和状态文件冲突，以代码和 Git 状态为准，并修正记录。
- 需求结束（合并/提 PR/丢弃）后，把它从 `CURRENT.md` 活跃索引移除，`local/active/<id>.md` 可归档到该需求目录。

## 敏感信息处理

联调和复盘时默认脱敏。

禁止落入 `shared`：

- 原始 cURL
- token
- cookie
- Authorization
- session
- 私密请求头
- 未脱敏响应
- 客户敏感数据
- 仅本机有效的临时路径

允许沉淀：

- 脱敏后的接口用途
- 请求方法
- 必要参数含义
- 响应字段含义
- 字段转换规则
- 错误处理经验
- 验证方式

写入共享文件、或分享/备份 `.tyflow` 前，AI 必须**逐条通读待写入内容做敏感信息自查**，命中以下任一即先脱敏再写入，绝不直接落盘：

```text
token / cookie / Authorization / Bearer / session / Set-Cookie
JWT（eyJ... 三段式）/ 私钥块（BEGIN PRIVATE KEY）
自定义认证头（X-*-Token / X-*-Key 等）带值
URL 查询串里的 token / access_token / sign / ak / sk
原始 cURL、未脱敏响应、客户敏感数据、仅本机有效的临时路径
```

完整策略与目标项目侧的 gitleaks 接入见 `shared/SECURITY.md`。

## 完成判定

完整提测准入门见 `shared/VERIFICATION.md`。只有同时满足以下条件，才能向用户说“完成”：

- 需求范围内的代码已经实现。
- 必要产物已经更新。
- 必要验证已经执行并通过。
- `TEST_CASES.md` 中 P0/P1 验收用例已经执行并通过；失败或阻塞项已经处理或明确记录。
- 未验证项和剩余风险已经写入 `VERIFY.md`。
- 接口字段不存在未确认的核心语义。
- 没有覆盖用户未确认改动。
- 需要复盘的内容已经写入 `RETRO.md`。

如果验证无法执行，只能说“实现已完成，验证未完成”，并说明原因和风险。

## 工作流自维护（AI 动作，非脚本）

Tyflow 是纯文档驱动的工作流，研发日常使用**不需要运行任何脚本**。但工作流文档自身也要保持自洽，这由 AI 在「修改工作流文档时」顺手完成：

每当 AI 新增/修改/删除 `shared/`、`baseline/`、`skills/` 下的文档或技能时，必须自查：

- **无幻影引用**：文档里提到的文件路径（如 `shared/PERFORMANCE.md`）、技能名（如 `api-contract-generator`）必须真实存在；指向不存在对象的引用立即修正或删除。
- **技能清单一致**：`shared/WORKFLOW.md`、`skills/README.md`、`REMADE.md` 三处的技能清单一致。
- **项目清单一致**：`shared/PROJECTS.md` 与 `shared/registry/commands.json` 的项目集合一致。
- **单一数值源**：性能阈值只在 `shared/PERFORMANCE.md` 写一份，其他文件只引用不复制。
- **无废弃名残留**：不再出现早期已废弃的子技能名（`tyflow-new-requirement`、`tyflow-plan-page`、`tyflow-verify-work` 等）和不存在的 `test-engineer`，除非是在说明"已废弃"。
- **历史归档不当真**：`workfile/` 与 `skills/document/` 下的旧执行版/蓝图是历史归档，**仅供复盘**。执行 tyflow 或检索规则/组件/经验时一律忽略它们，不得作为依据；凡与 `shared/` 冲突以 `shared/` 为准（这些文件已加归档警示头，且在 `RULES.md` 显式排除）。
- **同步最终介绍文档**：对工作流的能力 / 流程 / 门禁 / 文件结构做了实质改动时，必须同步更新 `workfile/Tyflow工作流-2.0版本总览.md`（最终对外介绍文档）和桌面 `Tyflow工作流-执行版说明.md`，保持二者与 `shared/` 一致——`shared/` 是事实来源，但这两份是研发和外部最先读到的入口，不同步会误导。

这是 AI 的自检清单，不是要谁去跑命令。发现不一致就地修复，保证下一位研发读到的工作流始终自洽。
