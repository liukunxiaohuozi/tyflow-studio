# 工程基线

开发过程中必须遵守的工程约束条件。本文件不是流程规则，而是编码和工程层面的事实标准。

## 目录结构

- 源码目录分层：`src/pages`（页面路由）、`src/components`（跨页面组件）、`src/services`（请求封装）、`src/models` 或 `src/store`（全局状态）、`src/utils`（纯函数工具）、`src/hooks`（可复用 hooks）、`src/locales`（国际化）、`src/constants`（常量枚举映射）。
- 页面目录模板：`src/pages/<domain>/index.tsx` + `config.ts` + `components/` + `hooks/` + `utils/` + `styles.less`。
- 路由统一集中管理（如 `config/routes.ts`），页面入口统一 `index.tsx`。
- 同类详情页统一交互模式，避免一个用抽屉、另一个用独立详情页。
- 状态管理边界：本地状态优先，全局状态最小化；命名要有业务语义，禁止 `data/list/info/temp` 这类弱命名。

## 请求层与服务层

- 所有接口请求定义在 `src/services/**`；禁止在页面和通用组件中直接调用 `fetch`/`axios`/`request`。
- 接口函数命名必须表达业务语义，禁止 `getData1` 这类模糊命名。
- 请求入参与响应数据必须定义 TypeScript 类型；协议变更时先更新类型与服务层，再修改页面调用。
- 服务层负责协议适配，页面层只消费可直接渲染的数据结构。
- 接口错误必须具备统一处理策略（消息提示、重试、降级展示），禁止吞错。
- 页面状态机：`loading` → `success` / `empty` / `error`。判定标准：`success` = HTTP 成功且业务状态成功；`empty` = 业务成功但无数据；`error` = 业务失败、HTTP 异常、超时或解析异常。`loading` 统一在 `finally` 或等价收口逻辑中关闭。
- 页面展示：`loading` 用 Spin 或骨架屏，`empty` 用空态组件，`error` 用错误态组件，`success` 用业务内容。

## 编码标准

### 代码质量

- 函数保持单一职责，复杂逻辑拆分为 hooks / utils。
- 避免魔法值，统一抽到常量。
- 文件超过 400 行时评估拆分。

### ESLint 防爆红

- 禁止先用后定义；JSX 中使用的函数必须先定义再使用。
- `useMemo`/`useEffect`/`useCallback` 里引用的方法和常量必须在上方已定义。
- 配置对象（columns、chart options）内引用的函数必须提前声明。
- 禁止用 `eslint-disable` 规避真实问题；如确需禁用必须有注释说明原因和影响范围。
- ESLint 报错修复顺序：移动到首次使用之前 → 改为函数声明 → 拆到独立 utils/hooks → 重新 lint 确认。

### TypeScript 规范

- 新增业务代码必须优先写明确类型，禁止"先 `any` 后补"。
- `any` 默认不允许使用；必须使用时缩小作用域并加注释说明原因。
- 请求入参、响应结构、核心业务对象必须定义类型；协议变更先改类型再改业务。
- 空值与可选值必须显式处理 `undefined`/`null`，不依赖隐式容错。
- 联合类型必须通过类型守卫收敛后再访问成员；禁止连续 `as unknown as` 强制断言。
- 业务离散值优先使用字面量联合类型或常量映射，不散落裸字符串/裸数字。

### 代码性能

- `useMemo` 仅在计算开销明显或需保持引用稳定时使用；`useCallback` 仅在传递给 memo 子组件或作为 `useEffect`/`useMemo` 依赖项时使用。简单计算和普通事件处理不强制使用。
- 列表项必须使用稳定 `key`，禁止随机 key；大数据场景优先虚拟滚动。
- 搜索、输入、滚动、拖拽等高频事件必须做防抖/节流。
- 请求按需发起，竞态场景要有过期保护，防止旧请求覆盖新状态。
- 复杂对象优先局部字段更新，多状态联动或状态流转复杂时优先 `useReducer`。
- 非首屏、不可见区域采用延迟渲染或按需渲染；抽屉、弹窗、折叠区内容默认按需挂载。
- 配置对象和常量避免在 render 中重复创建；高并发查找场景用 `Set.has(...)` 替代 `.includes`。

### 初始化应用逻辑

- 全局初始化逻辑（仅需执行一次、跨页面生效）禁止放入页面或业务组件的 `useEffect`/`useLayoutEffect`。
- 标准放置位置：纯逻辑放模块顶层；依赖浏览器对象加环境保护（`typeof window !== 'undefined'`）；依赖状态管理放状态层初始化方法。
- 初始化逻辑必须具备幂等性和清理机制。

## 样式规范

- 间距、字号、颜色优先使用 token 或语义变量（`--ty-*` 业务语义、`--ty-ant-*` antd 兼容映射），避免直接写固定色值和固定字号。
- 现有语义变量能表达的就不要再造新变量；只有主题体系未覆盖时才临时硬编码，并记录是否值得后续沉淀。
- 样式落位决策：先复用现有公共类和 token → 无法复用时写当前页面/组件的局部样式 → 仅当跨页面复用明确成立时才沉淀到全局。
- 全局样式文件只放：基础 reset/base、公共工具类、语义类与 token 映射、评审通过的第三方覆写。禁止把页面私有样式写入全局。
- 第三方组件样式覆写必须限制作用域，建议附注释说明目的和影响范围。

## Git 提交与 PR

- Commit message 格式：`<type>(<scope>): <summary>`。type 枚举：`feat`（新功能）、`fix`（缺陷修复）、`refactor`（重构）、`perf`（性能优化）、`test`（测试）、`docs`（文档）、`chore`（工程杂项）。
- 一个 commit 只做一类改动，功能改动与重构改动拆分，禁止混入无关大规模格式化。
- PR 必填：背景、方案、变更点、影响范围、回归说明。UI 改动附截图/录屏，接口改动附参数与返回字段变化说明，风险点与回滚方案。

## 分支管理

### 核心原则

- Tag 不从 `feature/xxx` 直接打。
- 公共版本 Tag 只从 `release/x.y` 打。
- 客户定制版本 Tag 只从 `custom/{客户简称}-{版本}` 或项目规定的定制分支打。
- 所有改动必须先完成开发、测试、Merge Request，再进入打 Tag 阶段。

### 开发环境判断

拿到需求后先确认：

1. 当前需求属于 SaaS 还是私有化。
2. 对应的基础分支或基础 Tag。
3. 需求分支是否已创建，未创建则基于基础分支或 Tag 创建。

如果这些信息未确认，视为阻塞项；先确认，再开始开发。

### 分支命名规则

- `release/x.y`：SaaS 主版本开发分支。
- `feature/xxx`：从对应 `release/x.y` 拉出的功能开发分支。
- `bugfix/xxx`：从线上问题对应 Tag 拉出的修复分支。
- `custom/{客户简称}-{版本}`：客户定制主分支。

### Tag 命名规则

公共版本：`v<主版本>.<次版本>.<修订号>-<YYMMDD>-<序号>`（示例：`v3.9.0-250901-1`）

客户定制版本：`v<主版本>.<次版本>.<修订号>-<客户代号>-<YYMMDD>-<序号>`（示例：`v2.14.0-JiDiaoWangLuo-250901-1`，客户代号不含汉字）

Bugfix：从问题对应 Tag 拉 `bugfix/xxx` → 修复 → MR → 合并回 `release/x.y` → 打新 Tag。多版本修复从低版本向高版本传播。

### 打 Tag 前检查

1. 改动已合并到正确的发布分支。
2. 当前分支不是 `feature/xxx` 临时分支。
3. 测试已通过。
4. 版本号和 Tag 命名正确。
5. 区分公共版本还是客户定制版本。
6. 确认项目是否要求由 CI/CD 或管理员创建 Tag。

### 私有化发包

私有化基础通常不是主干分支，而是发包对应的基础 Tag。通过 ReleaseGo（`https://releasego.tingyun.com/`）搜索客户/分叉或版本号，找到当前仓库对应 `Git TAG`。AI 无法访问时由研发手动提供。

## 反模式

- 页面或通用组件中直接发网络请求。
- 复制粘贴相同业务逻辑到多个模块。
- 只做 happy path，不处理异常态。
- 跳过 lint、类型检查和 i18n 扫描直接合并。
- 使用语义不清的文件名和变量名。
