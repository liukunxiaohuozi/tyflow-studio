# 观云 React 前端研发规范（完整参考）

## 0. 文档元信息

- 文档定位：观云 React 前端项目的公司级工程基线。
- 适用范围：所有 React + TypeScript 前端项目，含新建项目与存量项目治理。
- 推荐优先级：当目标仓库没有明确写法时，优先以本文件为默认工程标准。
- 冲突处理：若与目标仓库的真实约束或明确项目规范冲突，以目标仓库为准。
- 最后更新时间：2026-05-25

## 1. 文档定位

- 这是观云前端团队的公司级研发规范基线，适用于所有 React 前端项目（含存量项目与新项目）。
- 目标：统一工程结构、编码方式、联调流程、提交流程和交付质量，降低跨团队协作成本。

---

## 2. 适用范围

- 技术栈：`React + TypeScript`（含 Umi / Vite / Webpack 等工程形态）。
- 工作类型：新功能开发、需求迭代、缺陷修复、性能优化、重构、技术债治理。
- 协作场景：单人开发、多人并行开发、跨仓库联调、跨团队交付。

---

## 3. 核心原则（必须）

- 分层清晰：页面层、组件层、服务层、工具层职责明确。
- 统一入口：请求统一收敛到 `services` 层，禁止页面/组件直连网络层。
- 可复用优先：公共逻辑优先抽象，不复制粘贴业务逻辑。
- 可回归：每次变更必须可测试、可追踪、可回滚。
- 国际化优先：用户可见文案必须 i18n。

---

## 4. 标准目录规范

## 4.1 推荐分层

- `src/pages`：页面路由组件与页面级编排逻辑
- `src/components`：跨页面可复用组件
- `src/services`：接口请求封装与协议适配
- `src/models` 或 `src/store`：全局状态管理
- `src/utils`：纯函数工具与通用方法
- `src/hooks`：可复用 hooks
- `src/locales`：国际化词条
- `src/constants`：常量、枚举、映射关系

## 4.2 页面目录模板（建议）

```text
src/pages/<domain>/
  index.tsx
  config.ts
  components/
    XxxPanel/
      component.tsx
      index.ts
  hooks/
  utils/
  styles.less
```

---

## 5. 路由与页面规范

- 路由统一集中管理（如 `config/routes.ts`）。
- 页面入口文件统一 `index.tsx`。
- 详情页路由建议统一交互模式（如抽屉/弹窗/独立详情页），避免同类页面体验分裂。
- 页面必须定义：加载态、空态、错误态、无权限态。

---

## 6. 请求与数据层规范

## 6.1 请求放置规范

- 所有接口请求定义在 `src/services/**`。
- 禁止在页面和通用组件中直接调用 `fetch/axios/request`。
- 接口函数命名需表达业务语义，不使用模糊命名（如 `getData1`）。

## 6.2 协议与类型规范

- 请求入参与响应数据必须定义 TypeScript 类型。
- 协议变更时优先更新类型与服务层，再修改页面调用。
- 服务层负责协议适配，页面层只消费“可直接渲染的数据结构”。

## 6.3 异常处理规范

- 接口错误必须具备统一处理策略（消息提示、重试策略、降级展示）。
- 禁止吞错；至少保留日志或可观测信息。

## 6.4 接口状态兼容与页面态映射规范

- 每个请求必须具备“成功、空数据、业务失败、网络异常”四类兼容能力。
- 页面必须根据接口状态切换 UI 状态，禁止“请求失败但页面无反馈”。
- 本规范约束的是“状态处理能力”，不强制规定接口成功后的具体业务编排细节。

推荐页面状态机：

```text
loading -> success
loading -> empty
loading -> error
```

统一判定建议：

- `success`：HTTP 成功且业务状态成功（按接口契约判定）。
- `empty`：业务成功但无数据（空数组、空对象、关键字段缺失）。
- `error`：业务状态失败、HTTP 异常、超时、解析异常。

页面展示规范：

- `loading`：展示 `Spin` 或骨架屏。
- `empty`：展示空态组件。
- `error`：展示错误态组件。
- `success`：展示业务内容。

服务层规范：

- 服务函数返回值可被页面稳定判定。
- 不得把异常直接静默吞掉；`catch` 后至少返回可判定的失败结构或抛出标准错误。

页面层规范：

- 页面至少维护：
  - `loading`（按场景启用的加载状态）
  - `apiStatus`（如 `success / empty / error` 或等价枚举）
  - `data`（渲染数据）
- 默认情况下，请求应管理 `loading`，并在 `finally`（或等价统一收口逻辑）中关闭，避免在 `then/catch` 分散收口造成遗漏。
- 以下场景可不展示 `loading UI`：用户无感知请求、耗时极短请求、或不影响当前视图可用性的后台请求。
- 即使不展示 `loading UI`，仍需具备失败兜底与可追踪性，禁止静默失败。

建议封装（项目级通用）：

- 统一 `normalizeApiResult`（将不同后端协议归一到 `success/empty/error`）。
- 统一 `useRequestState` hook（内置 `loading/data/error/empty/retry`）。
- 统一错误码与错误提示映射（减少页面重复判断）。

## 7. 状态管理规范

- 本地状态优先：能在组件内解决，不提升到全局。
- 全局状态最小化：只放跨页面共享且高复用数据。
- 状态命名清晰，避免 `data/list/info/temp` 这类语义弱命名。

## 8. 组件与编码规范

## 8.1 组件职责

- 页面组件：负责页面编排、数据调度、路由交互。
- 业务组件：负责某块业务交互与展示。
- 通用组件：仅沉淀可复用能力，不绑具体业务域。

## 8.1.1 组件选型优先级

- 组件开发遵循“先复用、后封装、再自研”：
  1. 优先使用团队统一组件库已有能力。
  2. 组件库无法直接满足时，优先基于现有组件组合封装。
  3. 仅在现有能力确实不满足业务需求时，才新增自研组件。
- 禁止在已有等价组件能力时重复造轮子。
- AI 生成代码必须先匹配现有组件能力，再决定是否自定义实现。

## 8.2 命名与文件规范

- 组件目录与组件名使用 `PascalCase`。
- 组件主体建议 `component.tsx`，导出入口 `index.ts`。
- 配置文件统一 `config.ts` / `constants.ts`。

## 8.3 代码质量规范

- 函数保持单一职责，复杂逻辑拆分为 hooks / utils。
- 避免魔法值，统一抽到常量。
- 避免超大文件，建议超过 400 行开始评估拆分。

## 8.4 AI 编码防爆红规范（ESLint 零报错）

- AI 生成代码和人工代码都必须以“提交前无 ESLint 报错”为最低标准。
- 禁止先用后定义，避免触发 `@typescript-eslint/no-use-before-define`。
- JSX 中使用的函数（如 `renderXxx`、`handleXxx`）必须先定义再使用。
- `useMemo/useEffect/useCallback` 里引用的方法和常量，必须在上方已定义。
- 配置对象（如 columns、chart options）内引用到的函数，必须提前声明。
- 函数声明与箭头函数都可使用，不强制二选一；要求先定义后使用，并在同一文件保持风格一致。
- 禁止用 `eslint-disable` 规避真实问题；如确需禁用，必须有注释说明原因和影响范围。

## 8.5 ESLint 报错处理顺序（统一执行）

当出现类似 `'xxx' was used before it was defined` 报错时，按以下顺序修复：

1. 将函数/常量移动到首次使用之前。
2. 将函数表达式改为函数声明（适用时）。
3. 将公共逻辑拆分到独立 `utils/hooks` 后再引入。
4. 重新执行 lint，确认无新增告警和报错。

## 8.6 代码性能规范

- 渲染范围控制：
  - 避免父组件无关状态变更引发子树整体重渲染。
  - 重内容区域（表格、图表、复杂面板）优先拆成独立组件。
- 计算开销控制：
  - `useMemo` 仅在以下场景使用：
    - 计算本身开销明显（如大数组聚合、排序、复杂映射）。
    - 计算结果需要保持引用稳定（用于 memo 子组件或依赖项）。
  - `useCallback` 仅在以下场景使用：
    - 回调函数需要传递给 memo 子组件，且引用变化会导致无效重渲染。
    - 回调作为 `useEffect/useMemo` 依赖项，且需要稳定引用。
  - 避免滥用：简单计算和普通页面内事件处理不强制使用 `useMemo/useCallback`。
  - 配置对象和常量避免在 render 中重复创建。
  - 高并发查找场景（大量 `.includes` 重复判断）可将集合预处理为 `Set`，再使用 `set.has(...)`。
- 列表性能：
  - 列表项必须使用稳定 `key`，禁止随机 key。
  - 自定义大数据渲染场景（非通用表格组件）优先虚拟滚动；其次分页或分段渲染。
  - 默认避免一次性渲染超大数据集。
- 交互性能：
  - 搜索、输入、滚动、拖拽等高频事件必须做防抖/节流。
  - 避免高频事件中执行重计算或频繁 setState。
- 请求性能：
  - 请求按需发起，避免重复请求和无效请求。
  - 竞态场景要有过期保护，防止旧请求覆盖新状态。
- 状态更新性能：
  - 状态最小化，避免把局部状态提升到全局。
  - 复杂对象优先局部字段更新，减少整对象替换带来的重渲染。
  - 多状态联动或状态流转复杂时，优先 `useReducer` 管理状态迁移；简单状态不强制使用。
  - 读取外部可变数据源并需要订阅一致性时，使用 `useSyncExternalStore`；普通组件状态不使用。
  - 数据模型优先扁平化，减少深层嵌套带来的更新扩散与渲染成本。
- 可见性优化：
  - 非首屏、不可见区域采用延迟渲染或按需渲染。
  - 抽屉、弹窗、折叠区等内容默认按需挂载。

## 8.7 初始化应用逻辑放置规范

- 定义：初始化应用逻辑指“仅需执行一次、跨页面生效、与具体组件渲染无关”的全局逻辑。
- 约束：此类逻辑禁止直接放入页面或业务组件的 `useEffect/useLayoutEffect`。
- 目标：避免重复执行、生命周期时序不一致、以及组件职责污染。

适用范围：

- 读取全局持久化信息或应用级配置。
- 注册应用级事件监听与全局行为。
- 建立应用级长连接或全局通道。
- 注册全局默认配置与统一处理策略。

标准放置位置：

- 纯逻辑初始化：模块顶层（组件外部）。
- 依赖浏览器对象：模块顶层 + 环境保护（如 `typeof window !== 'undefined'`）。
- 依赖状态管理：放状态层初始化方法，由应用入口统一调用一次。

例外说明：

- 当初始化逻辑明确依赖某个页面的可见性或路由生命周期时，可放入页面层 effect。
- 该类例外必须在代码中注释原因，并保证幂等与可清理（`cleanup`）。

工程要求：

- 初始化逻辑应具备幂等性（重复调用不产生副作用叠加）。
- 全局监听与连接必须提供清理机制。
- 初始化失败需可观测（日志、上报或错误提示策略）。

## 8.8 TypeScript 规范

- 类型优先：新增业务代码必须优先写明确类型，避免“先 `any` 后补类型”。
- 禁止滥用 `any`：
  - 默认不允许直接使用 `any`。
  - 必须使用时，需缩小作用域并加注释说明原因。
- 接口契约前置：
  - 请求入参、响应结构、核心业务对象必须定义类型。
  - 协议变更先改类型，再改业务逻辑。
- 优先使用 `type`/`interface` 建模：
  - 对外数据结构、组件 Props、函数返回值必须显式声明。
  - 公共类型统一放在约定目录，避免重复定义同义类型。
- 空值与可选值处理：
  - 不依赖隐式容错，显式处理 `undefined/null`。
  - 可选链和空值合并仅用于“已确认可选”的场景。
- 类型收敛与保护：
  - 联合类型必须通过类型守卫收敛后再访问成员。
  - 禁止用强制断言掩盖真实类型问题（如连续 `as unknown as`）。
- 泛型使用原则：
  - 在可复用函数/组件中使用泛型保持类型透传。
  - 避免无约束泛型导致类型退化。
- 枚举与常量：
  - 业务离散值优先使用字面量联合类型或常量映射。
  - 避免在代码中散落裸字符串/裸数字状态值。
- 函数签名规范：
  - 函数参数与返回值类型尽量显式，减少隐式推断歧义。
  - 异步函数返回类型明确为 `Promise<T>`。

## 9. 样式规范

## 9.1 总原则

- 样式默认局部化，避免影响其他页面和组件。
- 全局样式最小化，只放基础能力和明确可复用能力。
- 新增样式优先使用设计 token，不新增无语义硬编码。
- 若涉及 `global.less`、页面 `index.less`、CSS Modules 与 `styles.xxx` 的具体项目口径，以 [project-standards-template.md](./project-standards-template.md) 的“样式落地约定”为准。

## 9.2 全局样式规范

- 全局样式文件只允许放：
  - 基础 reset/base
  - 公共工具类（如文本省略、对齐、通用间距）
  - 全局语义类与 token 映射
  - 明确评审通过的第三方样式覆写
- 禁止把页面私有样式写入全局。
- 禁止无边界全局选择器污染其他模块。

## 9.3 局部样式规范

- 页面样式放页面目录 `index.less`（或同级样式文件）。
- 组件样式放组件目录 `component.less` / `index.less`。
- 业务样式优先使用局部作用域写法（如 `styles.xxx`）。
- 不依赖全局类名拼装页面私有布局。

## 9.4 样式落位决策

新增样式按以下顺序处理：

1. 先复用现有公共类和 token。
2. 无法复用时写入当前页面/组件的局部样式。
3. 仅当跨页面复用明确成立时，才沉淀到全局样式。

## 9.5 token 与硬编码规范

- 新增代码：
  - 间距、字号、颜色优先使用 token 或语义变量。
  - 避免直接写固定色值和固定字号。
- 存量代码：
  - 允许逐步治理，不要求一次性重构。
  - 触达相关模块时优先顺手收敛到 token。

## 9.6 第三方样式覆写规范

- 覆写第三方组件样式时必须限制作用域。
- 新增覆写建议附注释说明目的和影响范围。
- 禁止在全局文件中做大范围无约束覆写。

## 9.7 可用性要求

- 页面在主流分辨率下应可用：不重叠、不遮挡、可滚动。
- 图表和表格区域需考虑最小宽度与溢出策略。
- 交互状态（hover/active/disabled/loading/empty）需有一致视觉反馈。

---

## 10. 国际化规范（强制）

- 用户可见文案必须走 i18n 体系。
- 新增文案需同步多语言词条。
- 提交前必须执行 i18n 扫描脚本（具体命令以项目级约定为准）。

---

## 11. 测试与质量门禁

- 单元测试：核心工具函数、关键业务逻辑必须覆盖。
- 组件测试：关键交互与状态切换必须可回归。
- 回归门禁：
  - lint 通过
  - 类型检查通过
  - 测试通过
  - i18n 扫描通过

## 12. Git 提交与 PR 规范（强制）

## 12.1 Commit Message

推荐格式：

```text
<type>(<scope>): <summary>
```

`type`：

- `feat`：新功能
- `fix`：缺陷修复
- `refactor`：重构
- `perf`：性能优化
- `test`：测试
- `docs`：文档
- `chore`：工程杂项

## 12.2 提交粒度

- 一个 commit 只做一类改动。
- 功能改动与重构改动尽量拆分。
- 禁止混入无关大规模格式化。

## 12.3 PR 要求

- 必填：背景、方案、变更点、影响范围、回归说明。
- UI 改动附截图/录屏。
- 接口改动附参数与返回字段变化说明。
- 说明风险点与回滚方案。

---

## 13. 标准研发流程

1. 需求澄清：边界、交互、数据来源、异常场景。
2. 技术方案：目录落位、接口设计、状态设计。
3. 编码实现：先服务层、后页面层、最后交互细节。
4. 联调验证：主流程、边界流程、失败路径。
5. 自测回归：质量门禁全通过。
6. CR 合并：完成评审意见与风险确认。
7. 发布跟踪：上线观察、告警关注、问题复盘。

---

## 14. 反模式（禁止）

- 页面中直接发网络请求。
- 复制粘贴相同业务逻辑到多个模块。
- 只做 happy path，不处理异常态。
- 跳过测试和扫描直接合并。
- 使用语义不清的文件名和变量名。

---

## 15. Skill 沉淀建议（工作流接入）

建议在前端工作流 skill 中固化以下阶段：

1. 任务识别：新功能/改造/修复/重构
2. 落位建议：涉及哪些目录与文件
3. 服务优先：先生成 `services` 改动方案
4. 页面接入：组件拆分、状态组织、交互实现
5. 质量门禁：lint、test、i18n、类型检查
6. 交付清单：PR 描述模板 + 自测清单
