# 开发环境与分支创建

## 文档元信息

- 文档定位：规范“拿到需求到开始开发前”的环境确认、基础分支或基础 Tag 定位、需求分支准备流程。
- 适用范围：新需求开发、缺陷修复、SaaS 改动、私有化发包改动。
- 推荐优先级：只要用户说“开发一个需求”，默认先读本文件。
- 冲突处理：若与项目负责人、当前仓库分支策略、ReleaseGo 页面信息冲突，以真实项目口径为准。
- 最后更新时间：2026-05-26

## 触发条件

出现以下任一情况时，先执行本 SOP，再开始开发：

- 用户说“开发一个需求”
- 用户说“修一个问题”
- 用户说“从某个版本做改动”
- 用户没有明确说明当前是 `SaaS` 还是私有化

## 输入项

开始前至少拿到这些信息中的一部分：

- 当前需求名称或需求背景
- 是否属于 `SaaS` 环境
- 是否属于私有化发包环境
- 客户名称 / 分叉名称
- 版本号
- 当前是否已经有人确认过基础分支或基础 Tag
- 当前是否已经打好了需求分支
- 如果需要访问 `ReleaseGo`，是否已有可用账号、密码或已登录会话

## 目标输出

执行完本 SOP 后，至少要明确：

1. 当前需求属于 `SaaS` 还是私有化
2. 对应的基础分支或基础 Tag
3. 是否已经存在可用的需求分支
4. 如果没有，应该基于哪里创建新分支
5. 本次开发最终应处于哪个需求分支上

## 前置条件

- 如果当前流程涉及 `https://releasego.tingyun.com/`，必须先具备可用登录态。
- 可用登录态包括以下任一项：
  - 可正常使用的用户名和密码
  - 当前浏览器中已登录的会话
  - 团队提供的可复用查询方式
- 如果没有登录态，AI 无法直接完成私有化 Tag 查询，此时应走降级流程。

## 分支创建命令示例

### SaaS 新功能

从 `release/x.y` 创建 `feature/xxx`：

```bash
git checkout release/3.9
git checkout -b feature/support-new-log-format
```

### SaaS 问题修复

从线上问题对应 Tag 创建 `bugfix/xxx`：

```bash
git checkout V3.9.0.19
git checkout -b bugfix/fix-null-pointer
```

如果修复不是从 Tag 开始，而是明确要求基于某个 `release/x.y` 修复，则以项目真实流程为准。

### 私有化需求开发

先确认私有化基础 Tag，再从该 Tag 创建需求分支：

```bash
git checkout V3.9.0.19-260210-1
git checkout -b feature/support-volvo-xxx
```

### 客户定制开发

如果项目使用 `custom/{客户简称}-{版本}` 主分支，先切到该分支，再拉功能分支：

```bash
git checkout custom/中信银行-3.9.10
git checkout -b feature/custom-citic-xxx
```

### 已有需求分支

如果需求分支已经打好，直接切过去：

```bash
git checkout feature/support-new-log-format
```

## 需求分支命名规则

默认参考 Git Flow 规范：

- `release/x.y`：SaaS 主版本开发分支
- `feature/xxx`：从对应 `release/x.y` 拉出的功能开发分支
- `bugfix/xxx`：从线上问题对应 Tag 拉出的修复分支
- `custom/{客户简称}-{版本}`：客户定制主分支

常见命名示例：

```text
release/3.9
feature/support-new-log-format
bugfix/fix-null-pointer
custom/中信银行-3.9.10
```

补充约定：

- 新功能开发：默认使用 `feature/xxx`
- 问题修复：默认使用 `bugfix/xxx`
- 客户定制开发：先确认是否已有 `custom/{客户简称}-{版本}` 分支，再决定后续功能分支命名
- 分支名里的 `xxx` 应尽量使用短语义英文短横线写法，不要使用无意义缩写

## 总判断树

```text
拿到需求
-> 判断分支是否已确认
  -> 已确认：检查是否已打好需求分支
    -> 已打好：直接在该分支开发
    -> 未打好：基于已确认的基础分支或基础 Tag 打需求分支
  -> 未确认：先判断是 SaaS 还是私有化
    -> SaaS：确认基础分支 -> 打需求分支
    -> 私有化：去 ReleaseGo 查基础 Tag -> 打需求分支
```

## SOP 1：分支已确认，检查需求分支是否已打好

### 适用场景

- 需求方、项目负责人或当前维护人已经明确告诉你基础分支或基础 Tag
- 或团队已经明确给出本次要使用的需求分支

### 执行步骤

1. 确认当前是基于基础分支开发，还是基于基础 Tag 开发。
2. 确认本次需求分支是否已经创建完成。
3. 如果需求分支已经创建完成，直接切到该分支开发。
4. 如果还没创建，则由当前开发者或 AI 基于已确认的基础分支或基础 Tag 创建需求分支。
5. 创建完成后，立即切换到该需求分支。

### 完成标准

- 已知道基础分支或基础 Tag
- 已知道需求分支名
- 已确认后续开发在哪个分支进行
- 当前工作区已经处于正确的需求分支上

## SOP 2：分支信息尚未确认

### 适用场景

- 用户只说“开发一个需求”，没有说明环境和分支
- 你不知道当前应该基于哪个版本开发
- 你不知道当前应该从分支还是 Tag 开始

### 执行步骤

1. 先确认当前需求是 `SaaS` 还是私有化。
2. 如果是 `SaaS`，执行下方“`SaaS` 环境开发 SOP”。
3. 如果是私有化，执行下方“私有化发包开发 SOP”。

### 默认提问顺序

1. 这是 `SaaS` 需求还是私有化需求？
2. 如果是 `SaaS`，当前基于哪个基础分支开发？
3. 如果是私有化，对应客户名称、分叉名称或版本号是什么？
4. 私有化对应的基础 Tag 是哪个？
5. 本次需求分支是否已经创建？

## SOP 3：SaaS 环境开发

### 前提

- 当前需求明确属于 `SaaS`

### 执行步骤

1. 确认 `SaaS` 环境当前要求基于哪个基础分支开发。
2. 如果需求分支已经存在，确认该分支就是基于正确基础分支创建的。
3. 如果需求分支不存在，基于该基础分支创建本次需求分支。
4. 创建完成后，立即切换到该需求分支。
5. 所有后续开发都在该需求分支上进行。

### 关键点

- 不要默认从当前本地分支开始开发。
- 不要跳过“基础分支确认”。
- 如果 `SaaS` 分支策略有变更，以项目当前维护人或项目文档为准。

### 完成标准

- 已确认 `SaaS` 基础分支
- 已确认或已创建需求分支
- 当前已切换到需求分支

## SOP 4：私有化发包开发

### 前提

- 当前需求明确属于私有化环境

### 推荐模式

- 优先模式：AI 自动查询 `ReleaseGo`，提取当前仓库对应的基础 Tag，再由研发确认。
- 降级模式：如果 AI 当前无法访问 `ReleaseGo`，再由研发手动提供客户名、版本号或基础 Tag。
- 前提：优先模式只有在 AI 具备可用登录态时才成立。

### 执行步骤

1. AI 优先打开 `https://releasego.tingyun.com/`
2. AI 搜索对应的分叉名称。
   - 例如：`沃尔沃`
3. 或搜索对应的版本号。
   - 例如：`3.9.0.22`
4. AI 在搜索结果中找到最新记录，点击查看。
5. AI 在详情中找到 `Git TAG` 列。
6. AI 找到当前仓库对应的 Tag。
   - 例如 `app-web` 对应的 Tag 可能是 `V3.9.0.19-260210-1`
7. AI 输出结论给研发确认：
   - 当前识别到的私有化基础 Tag 是什么
   - 本次开发是否应基于这个 Tag 创建需求分支
8. 如果研发确认无误：
   - 需求分支已存在：确认该分支就是基于这个基础 Tag 创建的
   - 需求分支不存在：基于该基础 Tag 创建本次需求分支
9. 创建完成后，立即切换到该需求分支。
10. 所有后续开发都在该需求分支上进行。

### 降级流程

如果 AI 当前无法访问 `ReleaseGo`，或没有可用登录态，则改为：

1. 由研发提供客户名称、分叉名称、版本号或基础 Tag。
2. 如果研发只提供客户名称或版本号，则由研发手动去 `ReleaseGo` 查对应 Tag。
3. 研发把基础 Tag 提供给 AI。
4. AI 基于该 Tag 创建并切换需求分支。

### 关键点

- 私有化开发的基础通常不是主干分支，而是发包对应的基础 Tag。
- 搜索时优先使用客户/分叉名称或版本号。
- 一定要确认看的 `Git TAG` 是当前仓库对应的，不要看错仓库。
- 最稳妥的模式是：AI 自动查询 -> 研发确认 -> AI 创建并切换需求分支。

### 完成标准

- 已确认私有化基础 Tag
- 已确认或已创建需求分支
- 当前已切换到需求分支

## 建议沉淀到项目级约定里的固定信息

- 合并目标分支规则

## 示例

### 示例 1：SaaS，分支未创建

```text
需求 -> 确认是 SaaS -> 确认基础分支 -> 创建需求分支 -> 开发
```

### 示例 2：私有化，分支未创建

```text
需求 -> 确认是私有化
-> 打开 https://releasego.tingyun.com/
-> 搜索“沃尔沃”或“3.9.0.22”
-> 找到最新记录并查看
-> 找到 app-web 对应 Git TAG，例如 V3.9.0.19-260210-1
-> 基于该 Tag 创建需求分支
-> 开发
```

### 示例 3：分支已打好

```text
需求 -> 已知基础分支或基础 Tag
-> 已知需求分支已创建
-> 切到该需求分支
-> 开发
```
