# 编码质量、样式与交付规范

## 文档元信息

- 文档定位：聚合工程中的编码约束、样式落位、国际化、测试门禁和提交流程。
- 适用范围：编码实现、重构、代码评审、交付前自检。
- 推荐优先级：提交代码前应至少快速过一遍本文件。
- 冲突处理：若目标仓库有更严格门禁，以目标仓库为准。
- 最后更新时间：2026-05-25

## 组件与编码

- 页面组件负责页面编排、数据调度、路由交互。
- 业务组件负责业务交互与展示。
- 通用组件只沉淀可复用能力，不绑定具体业务域。
- 组件选型遵循“先复用、后封装、再自研”。

## 命名与文件

- 组件目录与组件名使用 `PascalCase`。
- 组件主体建议 `component.tsx`，导出入口 `index.ts`。
- 配置文件统一 `config.ts` 或 `constants.ts`。

## 代码质量与性能

- 保持单一职责，复杂逻辑拆到 hooks 或 utils。
- 避免魔法值，统一抽常量。
- 文件超过 400 行时应评估拆分。
- `useMemo / useCallback` 只在确有开销或引用稳定需求时使用，避免滥用。
- 高并发查找场景优先 `Set.has(...)`。
- 高频交互需要防抖或节流。
- 不可见区域采用按需挂载或延迟渲染。

## 样式与国际化

- 样式落位、`global.less` 复用、页面 `index.less` 与 `styles.xxx` 的具体口径，以 [project-standards-template.md](./project-standards-template.md) 的“样式落地约定”为唯一真源。
- 间距、字号、颜色优先使用 token。
- 用户可见文案必须走 i18n。
- 详细视觉规则请转到 `design/` 目录。

## 测试与质量门禁

- lint 通过。
- 类型检查通过。
- 测试通过。
- i18n 扫描通过。

## Git 与研发流程

- Commit 推荐格式：`<type>(<scope>): <summary>`。
- 一个 commit 只做一类改动，避免无关格式化混入。
- PR 至少写清背景、方案、影响范围、回归说明。

标准研发流程：

1. 需求澄清
2. 技术方案
3. 编码实现
4. 联调验证
5. 自测回归
6. CR 合并
7. 发布跟踪

## 反模式

- 页面直接发网络请求。
- 复制粘贴相同业务逻辑。
- 只做 happy path，不处理异常态。
- 跳过测试和扫描直接合并。
