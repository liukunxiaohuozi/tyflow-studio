# 测试工程师技能

## 执行路由

- 收到 `verificationMode: orchestrated` 时，作为 Studio 配置的测试提供者执行一次正式验证，严格按调用方冻结的代码快照、计划与用例返回证据；不重新解释需求，不重复开发阶段反馈检查，是否复用由 Studio 判断。
- 未收到编排标识时保持当前完整原生验证流程。即使机器没有 Studio 和 `frontend-test`，本技能也必须独立完成下述硬检查、用例、覆盖度、页面与性能验证，不得降级成空壳或仅转发入口。
- 若外部结果缺少必测用例或证据，只补充缺口；无法证明身份或范围时执行完整原生验证。

本技能定义 AI 如何像测试工程师一样系统性验证前端开发产物。

## 适用场景

- L2/L3 开发完成后的验证阶段
- 用户说「帮我验证」「跑一下验证」「可以提测了吗」
- Step 15（完成前验证）的执行指南

## 核心原则

1. **验证不是 AI 说「通过了」就通过了**——每条声明必须有原始证据
2. **硬检查不可跳过**——编译、lint、测试、构建的输出是机器生成的，AI 无法伪造
3. **理解偏差是最大风险**——如果 AI 理解错了需求，验证再完整也是白费
4. **「可以提测」≠「没有 bug」**——它意味着自动化验证全部通过，需求覆盖完整

## 验证前准备

验证开始前，必须先读取以下文件：

1. `REQUIREMENT.md` — 需求条目和验收标准
2. `TEST_CASES.md` — 测试用例和优先级
3. `PLAN.md` — 理解确认和任务拆分
4. `CONTRACT.md` — 接口契约（如果有）
5. `baseline/design.md` — 设计 Token（如果涉及样式）

如果上述文件不存在或未完成，暂停并提示用户先补齐。

## 验证循环

严格按以下顺序执行。任何一步失败，修复后从失败步骤重新开始，不需要从头跑。

### 第一关：硬检查

这些检查的输出是机器生成的二值结果（通过/失败），AI 无法伪造。

```
① TypeScript 编译
   命令：tsc --noEmit（或 PROJECTS.md 中登记的类型检查命令）
   通过条件：0 errors
   证据：粘贴完整命令输出

② ESLint
   命令：eslint（或 PROJECTS.md 中登记的 lint 命令）
   通过条件：0 errors（warnings 允许但需记录）
   证据：粘贴完整命令输出

③ 单元测试
   命令：jest（或 PROJECTS.md 中登记的测试命令）
   通过条件：所有测试 PASS，0 FAIL
   证据：粘贴命令输出，必须包含 Tests: XX passed, XX total 行

④ 构建
   命令：npm run build（或 PROJECTS.md 中登记的构建命令）
   通过条件：构建成功，无错误
   证据：粘贴完整命令输出
```

硬检查失败时的处理：
- 记录失败原因到 VERIFY.md
- 修复代码
- 只重跑失败的检查项（不需要重跑已通过的项）
- 修复引入新失败时，新失败也必须解决

### 第二关：测试用例执行

按 `TEST_CASES.md` 逐条执行 P0/P1 用例。

执行方式取决于用例的「验证方法」列：

| 验证方法 | 执行方式 | 证据 |
|---------|---------|------|
| jest | 运行对应测试文件 | 粘贴 jest 输出 |
| Playwright DOM | 打开页面，读取 DOM 快照，检查元素 | DOM 快照 + 关键元素文本 |
| Playwright CSS | 打开页面，读取 computed style | 实际 CSS 值 vs Token 预期值 |
| Playwright 交互 | 模拟点击/输入，检查状态变化 | 操作前后的 DOM 快照对比 |
| API 对比 | 对比 API 响应与 UI 展示字段 | API 响应片段 + UI 文本 |
| 人工 | 标记为「需人工确认」 | 列出待确认项 |

每个用例执行后，记录：
- 用例 ID
- 实际结果（描述具体观察到的现象，不是「通过」两个字）
- 原始证据（DOM 快照、测试输出行号、截图）
- 判定（✅ / ❌）

P2 用例可选择性执行，未执行的必须说明原因。

### 第三关：需求覆盖度

回溯 `REQUIREMENT.md` 中每条需求，检查：

1. 是否有对应的测试用例
2. 测试用例是否已执行通过
3. 代码实现是否存在

每条需求标记：
- **已覆盖**：有对应用例，已执行通过
- **部分覆盖**：有用例但只覆盖了部分场景（说明缺失内容）
- **未覆盖**：无对应用例或用例未通过（说明原因）
- **已变更**：需求在开发过程中发生了变更（说明变更来源和新范围）

存在「未覆盖」或「部分覆盖」的核心需求时，不能宣布完成。

### 第四关：Playwright 页面验证（可选）

仅在有 dev server 运行时执行。无 dev server 时标注跳过原因。

使用 Playwright MCP 执行：

1. **页面可访问性**：打开目标 URL，确认页面正常渲染（无白屏、无 JS 错误）
2. **关键元素存在**：读取 accessibility tree，确认核心组件（表格、表单、图表、按钮）存在
3. **文案正确性**：读取关键文本内容，与 REQUIREMENT.md 中的文案要求对比
4. **样式 Token**：读取关键元素的 computed style，与 `baseline/design.md` 中的 Token 值对比
5. **交互正确性**：模拟关键操作（点击、输入、导航），检查状态变化是否符合 SPEC.md

每个验证项记录：验证项、验证方法、预期值、实际值、证据、判定。

### 第五关：性能指标验证

有 dev server 时必须执行。无 dev server 时标注「性能未验证」并列出风险点。

验证方式：
- **Lighthouse CLI**：`npx lighthouse http://localhost:PORT --output=json --quiet`，从 JSON 中提取 FCP、LCP、TBT、CLS 和 Performance 分数
- **Performance API**：在 Playwright 中执行 `JSON.stringify(performance.getEntriesByType('navigation'))`，获取 FCP、LCP 等
- **Lighthouse 评分取 3 次中位数**（单次波动大）

及格线（硬门槛，不达标不能宣布完成）：

| 指标 | 及格线 | 目标线 |
|------|--------|--------|
| FCP（白屏结束） | ≤ 2.0s | ≤ 1.0s |
| LCP（主内容可见） | ≤ 3.0s | ≤ 2.5s |
| INP（交互响应） | ≤ 300ms | ≤ 200ms |
| CLS（布局偏移） | ≤ 0.15 | ≤ 0.1 |
| TBT（阻塞时间） | ≤ 400ms | ≤ 200ms |
| Lighthouse Performance | ≥ 80 | ≥ 90 |

每个指标记录：指标名、及格线、实际值、证据（Lighthouse 输出片段或 Performance API 数据）、判定。

性能不达标时的处理：
1. 分析瓶颈来源（接口慢 / 包体积大 / 同步渲染重 / 图表计算多）
2. 可修复的修复后重跑
3. 无法立即修复的，记录瓶颈分析和风险到 VERIFY.md
4. FCP 超标时必须有骨架屏兜底
5. 详细指标来源和阈值依据见 `shared/PERFORMANCE.md`

### 第六关：输出验证报告

将以上所有结果写入 `VERIFY.md`，严格按模板格式：

```
## 1. 硬检查
- 每项附带命令原始输出

## 2. 测试用例执行
- 每条用例附带实际结果和原始证据

## 3. 需求覆盖度
- 每条需求追溯对应用例 ID 和实现位置

## 4. 页面验证
- 每项附带 DOM 快照或 CSS 实际值

## 5. 性能指标
- 每项附带实际值和 Lighthouse 输出
- 无 dev server 时填写风险清单

## 6. 未验证项与剩余风险
- 列出无法自动验证的项目

## 结论
- 五项复选框全部勾选 → 「可以提测」
- 任一未勾选 → 「实现已完成，验证未通过」或「部分验证需人工确认」
```

## 修复循环

当验证发现问题时：

1. 记录失败项到 VERIFY.md 的对应章节
2. 修复代码
3. **只重跑失败的检查项和用例**，不需要重跑已通过的
4. 修复可能引入新的失败，新失败也必须解决
5. 所有失败项解决后，更新 VERIFY.md 的判定
6. 不得在修复过程中删除或隐藏原始失败记录

## 「可以提测」的通过标准

只有五项全部满足才能输出「可以提测」：

- [ ] 所有硬检查通过（tsc 0 errors, eslint 0 errors, jest 0 fail, build 成功）
- [ ] TEST_CASES.md 中 P0/P1 用例全部执行并通过
- [ ] REQUIREMENT.md 中所有核心需求已覆盖（无「未覆盖」的核心需求）
- [ ] 性能指标达到及格线（FCP ≤ 2.0s, LCP ≤ 3.0s, CLS ≤ 0.15 等），或无法验证时风险已记录
- [ ] 未验证项和剩余风险已明确记录在 VERIFY.md

不满足时只能输出：
- 「实现已完成，验证未通过」—— 验证发现具体问题
- 「实现已完成，部分验证需人工确认」—— 有些项只能人工判定

## 验证造假防护

以下行为视为验证造假，严格禁止：

- 硬检查只写「已通过」不粘贴命令输出
- 测试用例只写「通过」不描述实际结果和证据
- 需求覆盖度只写「已覆盖」不追溯对应用例 ID
- 跳过失败的检查项不记录
- 修复后删除原始失败记录

检测方式：用户只需抽查 VERIFY.md 中任意 2-3 条声明，检查是否有对应的原始证据。如果没有，说明验证过程不可信。

## 信任边界说明

本技能能保证的：
- TypeScript 类型错误被拦截
- ESLint 规范问题被拦截
- 单元测试覆盖的逻辑错误被拦截
- 关键 UI 元素缺失被拦截
- API 字段映射错误被拦截（通过类型和测试）
- 需求遗漏被拦截（覆盖度追踪）

本技能无法保证的（需要人工兜底）：
- AI 对业务逻辑的理解偏差
- 视觉主观判断（间距差 2px 算不算问题）
- AI 没想到的边界场景
- 多浏览器兼容性
- 交互「手感」（动画流畅度、微交互）
- 性能基准测试

## 与其他技能的协作

- `tyflow-verify-work`：触发本技能的入口
- `tyflow-review`：代码审查，在验证前或验证后执行
- `tyflow-retro`：复盘时引用 VERIFY.md 的验证结果和度量数据
- Playwright MCP：提供浏览器控制能力（DOM 快照、CSS 读取、交互模拟）
